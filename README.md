# 美团骑行截图轨迹识别

从美团骑行 App 的**地图截图**中还原骑行轨迹，输出 GeoJSON。

GPS 坐标不在图片里——截图只是一张渲染好的地图。本项目用图上已知的地理参照物
（POI 标注、地铁站、比例尺）作为锚点，把「像素坐标系」配准到「经纬度坐标系」，
再把提取出的轨迹像素折线反投影为 GPS 点序列。

---

## 📘 交接文档

**接手本项目请先读 [`docs/HANDOVER.md`](docs/HANDOVER.md)** ——
完整的项目设计、模块职责、坐标系约定、算法细节、API 契约、
已知坑与排障手册、决策记录。

GPS 坐标不在图片里，要用图上印的 POI 标注当锚点做像素→经纬度映射，
再用真实路网约束校正。

## 准确率评测与置信度校准

「贴路距离变小、锚点残差变小、confidence 变高」都只是**自洽指标**：把一条
起终点直线整体平移到平行主干道，三者会一起变好，真实位置却更错（§22.38）。
所以这一轮优化先用外部真值把「准不准」变成可证伪的量，再谈提升。

```bash
# 合成真值基准：带已知变换 / 噪声 / 离群点 / OCR 残片，CI 可直接跑
python src/tools/eval_accuracy.py --synthetic 20 --out output/eval_baseline.json

# 真实样本：识别结果 JSON + 真值 GPX / GeoJSON
python src/tools/eval_accuracy.py --pred data/last_result.json \
    --truth samples/truth.gpx

# 与基线比 P50（同一 --seed0 才有意义）
python src/tools/eval_accuracy.py --synthetic 20 \
    --compare output/eval_baseline.json

# 用 ≥8 组 (识别结果, 真值) 拟合置信度校准曲线
python src/tools/calibrate_confidence.py \
    --case "data/result_a.json|samples/truth_a.gpx" \
    --case "data/result_b.json|samples/truth_b.gpx" \
    --out data/confidence_calibration.json
python src/tools/calibrate_confidence.py --show     # 看当前校准状态
```

指标：起终点误差、离散 Fréchet 距离、里程相对误差、配准尺度/中心误差、
内点 precision/recall。校准用 PAVA 保序回归 + 收缩混合，把启发式
confidence 映射到「达到误差门槛的经验成功率」。

> **没有真值就没有校准**：模型文件缺失、样本不足 8 组、内容损坏或非单调时，
> 服务端**原样返回**原置信度，`diagnostics.confidence_calibration.status`
> 显示 `uncalibrated`。模型路径可用 `RIDE_CONFIDENCE_CALIBRATION` 覆盖，
> 改完文件无需重启（按 mtime 热加载）。
>
> 同理，`data/lexicon.json` 的自动写入要等识别结果出来、通过置信度与
> 自洽门槛才落盘；`diagnostics.lexicon_write_guard` 会记录本轮通过/否决
> 数量与原因。详见交接文档 §22.40。

## 路网约束精修（关键一步）

配准的锚点是 **POI 文字标注**，而标注位置由地图排版决定，且 POI 坐标来自
不同数据库：美团底图用高德/腾讯的国内 POI 数据，而词典种子来自
OSM/Nominatim。同一 POI 在两套数据里可差 100-300 米。

实测长宁新泾一例：锚点全部来自 OSM POI 点，配准整体偏了约 326 米，
轨迹落到了**平行的错误道路族**上——用户实骑 新渔路/新渔东路/剑河路/金钟路，
而 OSM 归属显示 天山路/北翟路/淞虹路。两者几何一致、命名不一致，
贴路看起来都"还行"，只有用户知道骑的是哪条路。

修法分两步：

1. **修正地理编码优先级**（`src/app/geocode.py`）：用户确认 > 在线服务（与美团
   底图同源）> 本地词典。早期实现是「词典优先」，只要词典命中就永不调用
   在线服务，配了 `AMAP_KEY` 也用不上——这是根因。
2. **路网约束精修**（`src/app/roadfit.py`）：道路几何不存在基准不一致的问题。
   在保持尺度与朝向的前提下平移轨迹，使贴路距离最小，再把平移量并入配准
   矩阵。实测贴路中位距离 61 m → 5 m，路名归属随即输出为用户实骑的那几条。

这一步同时解决了「这条轨迹骑的是哪几条路」——它是轨迹与真实路网的
几何并集，比任何 POI 查询都可靠。

**教训**：单一指标变好 ≠ 位置更准。当时曾用「平移后贴路距离最小」找最优解，
方向是对的；但用「到 OSM 最近顶点的距离」当判据时出现了假阴/假阳——
只测"到最近点"而不测"线路是否沿这个方向延伸"，会把一个恰好存在的顶点
误当成吻合。

## 坐标系转换：一个让整条链路偏 400 米的 bug

`src/app/geo/coords.py` 里的 GCJ-02 转换曾经有一个**万里挑一的实现错误**：

```python
dlat, dlon = _transform_lat(lon - 105.0, lat - 35.0)   # ← dlon 也取了 lat 的结果
```

`_transform_lat` 返回 `(ret, ret)`，所以 **`dlon` 拿到的是纬度变换的值**——
`_transform_lon` 是死代码，从未被调用。这个错误被"两个值相同"完全掩盖住了，
所有看起来正常的测试都通过。

代价有多大：纬度精确，**经度偏差 375 米**。上海实测 GCJ-02 偏移应为
**东 +438 m、南 −208 m**，错误版本算出的是东 −207 m——**方向都反了**。

更糟的是这个偏差会进入**每一个锚点**，然后被"路网约束精修"当成真实位置误差
去纠正，于是整条轨迹被推到了平行的错误道路族上。

**怎么发现的**：用公开的权威基准点校验——

```
天安门  WGS-84 (116.391349, 39.907375)  →  GCJ-02 (116.397590, 39.908776)
```

修复后误差 **0.0 m**。这条断言现在写进了 `tests/test_e2e.py`，
是最先能抓住此类问题的守门测试。

**教训**：涉及坐标系转换的代码，**必须用外部权威基准点做单元测试**，
不能只验证「往返无损」——往返无损在错误实现下同样成立。

顺带修掉的还有 `roadfit.py` 里的基准混用：轨迹是 GCJ-02 墨卡托，
OSM 路网是 WGS-84 墨卡托，两者直接比较会引入约 470 米的伪偏移。

## 支持的路线形状：不要再用「横向延展」当启发式

早期连通域筛选要求轨迹的包围盒 **aspect > 1.6**（横向延展）。这在第一张
样本（东西向长距离）上碰巧成立，但对**对角线或南北向路线会整条漏掉**——
第二张样本 aspect ≈ 1.03，管线直接返回「未找到轨迹连通域」。

现在改成拓扑驱动：

1. 用包围盒粗筛候选（同时靠近两个徽章、面积够大）
2. 对最接近的若干候选做**像素级精确测距**：连通域到「起」「终」两个徽章的
   最近像素距离
3. 取总距离最小者；超过 260 px 则判定「不是轨迹」

退化情况（未检出徽章）用「填充率」筛掉文字团块。

## 输出坐标的反投影必须与提取轨迹重合

交付可视化时踩过两次同样的坑：**把已经是 GCJ-02 的坐标又做了一次
`wgs84_to_gcj02`**，凭空多出约 500 米（100+ 像素）的偏移，画出来轨迹明显
偏离原图，还以为是算法错了。

现在 `tests/test_e2e.py` 里有一条断言守住它：**输出坐标反投影回像素后，
必须与提取的轨迹像素重合（阈值 3 px，实测中位 0.24 px）**。
同理，校验绝对位置时也绝不能重复换算基准。

## 换一张截图就崩：三个叠加的坑

换成新区域的截图后，页面直接报
`识别失败：Cannot read properties of undefined (reading 'toFixed')`。
这句话本身没有信息量——它是一层**假象**，真正的失败在下面三层。

### ① 前端：失败响应没有字段，前端又直接 `.toFixed()`

后端在配准失败时只返回 `diagnostics = {"track_points": N}`，
前端却直接写 `dg.rotation_deg.toFixed(2)` → `undefined.toFixed` 抛 TypeError
→ 被 `catch` 捕获 → 显示成「识别失败」。

**后果比报错本身严重**：真正的失败原因（`warnings` 里写着
「所有锚点均未匹配到坐标」）被这个异常整个吞掉，用户无从得知发生了什么。

修法有两条，缺一不可：

- 后端所有失败路径都返回**结构一致**的 diagnostics（`DIAG_KEYS` + `_base_diagnostics`）
- 前端所有数值字段走安全格式化（`num()` / `int()` / `text()`），缺失显示「—」

顺带修掉的同类崩溃点：`drawMap` 在空几何上取 `features[0]`、
`drawPreview` 用 `image_size=[0,0]` 做除法、失败时 `warnings` 未做 HTML 转义。

### ② 后端：新区域没有坐标来源

词典只有已核验的 38 个上海地名，新截图里的「安龙小区」等全都不在其中，
又没配地图密钥 → 0 个锚点 → 配准失败。

补上 **OSM 冷启动**（见「③ 地理编码」）。修复后同一张截图：

```
置信度 0.791   轨迹点 43   里程 447.9 m
贴路中位距离 2.8 m → 2.3 m
经过道路：新渔东路 → 安龙路        ← 与截图上印的路名一致
```

### ③ 算法：两个与「尺度」有关的隐藏 bug

新截图是**高倍截图**（`scale = 0.22 m/px`，而旧样本是 4.5 m/px），
暴露了两处只在小尺度下才发作的问题：

**采样步长与简化容差没有像素上限。** 10 米的步长在 `scale=0.26` 时
换算成 38 像素，一个弯道就被跳过；2 米的容差变成 7.7 像素，把弯道全削平了
——1990 像素的轨迹最后只剩 **6 个点**。现在两者都加了像素上限
（步长 ≤ 4 px，容差 ≤ 1 px）。

**经典 Douglas-Peucker 在近直线上失效。** 它用「到端点连线的垂距」作判据，
而一条南北向长直线上任何微小横向抖动都会被这段长直线放大成很大的垂距。
实测轨迹总长 2043 像素、端到端直线 1954 像素（仅 4.5% 蛇形），
简化后只剩 32 个点，弯道全部消失。

改用**弧长偏差**作主判据（折线比弦长多走了多少路，与「直线很长」无关），
垂距只用来定位分裂点。实测弧长保留 98.5%，最大偏离原轨迹 0.54 像素。

### 顺带修掉的坐标系 bug

`_road_refine` 把 `reg.pixel_to_lonlat()` 的 **GCJ-02** bbox 直接喂给
OSM API（它期望 **WGS-84**），查询中心因此偏移约 450 米（东）/200 米（南），
拉回来的是**别的街区**的路网。现在先转 WGS-84 再查询。

> **教训**：这三个 bug 有同一个共同特征——**只在旧样本上看不出来**。
> 旧样本尺度大（4.5 m/px）、区域在词典内、且必然成功。
> 换一张截图就同时踩中三个。**必须用不同区域、不同缩放级别的多张图来验证。**

## 只在浏览器里才会犯的两个 bug

这两个问题的服务端日志**全是 200**——识别本身是成功的，错误发生在
识别完成之后的渲染阶段。所以跑后端测试永远发现不了。

### 连续识别报「Unhandled error. (undefined)」

**真正的根因是腾讯地图鉴权失败，不是「连续识别」本身。**

`Unhandled error. (undefined)` 这句话来自 Node.js 的 `EventEmitter` 标准实现：

```js
var s = new Error("Unhandled error." + (a ? " (" + a.message + ")" : ""));
```

即某个组件触发了 `'error'` 事件但**没有监听器**，且第一个参数不是 `Error` 实例。
腾讯地图 GL JS 鉴权失败时走的正是这条路。

**鉴权为什么会失败**：`src/web/index.html` 里的

```js
serviceHost: 'http://127.0.0.1:__WB_HTTP_PORT__/_TMapService/_wbt/__WB_TMAP_SECRET__',
```

这两个占位符**从来没有被任何代码替换过**——README 承诺的「本地代理」
根本不存在。SDK 于是去请求一个非法地址（`__WB_HTTP_PORT__` 不是合法端口），
鉴权必然失败 → SDK 内部 `AUTH_ERROR.netError` → 触发 `'error'` 事件 →
抛出没有上下文的 `Unhandled error. (undefined)`。

而我们的 `catch` 把它包装成了「识别失败」——**把一个底图问题说成了识别问题**。

**修法**：

1. 实现 `src/app/tmap_proxy.py`：真实转发 `checkKey` / `oversea` / `pingd` 到腾讯地图上游，
   在服务端注入 key，浏览器永远拿不到 key
2. 首页改为动态渲染（`src/app/server.py` 的 `index()`），把端口与随机代理标记填进页面
3. 底图 key 用腾讯地图官方公开示例 key（`config.TMAP_PUBLIC_KEY`），
   用户配了自己的 `TMAP_KEY` 则优先用用户的
4. **把「识别」与「渲染」彻底分开**：接口失败才显示「识别失败」；
   渲染失败只提示「识别已完成，但地图渲染出错，GeoJSON 可正常下载」
5. 附加防护：容器尺寸为 0 时不操作地图、`fitBounds` 加尺寸检查与 try-catch、
   识别完成后调用 `ensureMapReady()` 确保地图就绪

> **教训一**：README 里写了「腾讯地图 GL JS 走本地代理」——但代码里没有。
> **文档描述了一个不存在的实现，比没有文档更糟**，因为它让人以为底图是正常的。
>
> **教训二**：第三方 SDK 的错误信息可能完全没有上下文。
> 遇到 `Unhandled error. (undefined)` 这类消息，第一反应应该是
> **「这到底是谁抛的？」**——用 grep 在项目里搜这个字符串，零命中就说明不是我们的代码。
>
> **教训三**：真实浏览器测试是唯一可靠的手段。
> 前两轮修复（容器尺寸检查、隐藏时跳过）方向都对但都不是根因，
> 只有 Playwright 抓到真实的 `pageerror` 才定位到真相。
> 见 `src/tools/verify_browser.py`。

### 原图预览下半部分显示不全

`#preview` 原本和 `#map` 共用 `height:480px; overflow:hidden`。
而截图是 **1260×2720 的竖长图**，按宽度缩放后高度远超 480px，
下半部分被直接裁掉。

修法：`#preview` 拆出来单独设样式，高度由图片本身撑开。
顺带修了画布尺寸——原先只设了 `style.height` 而 CSS 里是 `height:100%`，
两者打架导致叠加的轨迹与原图错位。

> **教训**：这类纯前端的 bug 必须单独测。
> `tests/test_frontend.py` 把 `index.html` 的函数抽出来，
> 配一个会复现真实腾讯地图行为的桩，逐场景断言（29 项）。
> 它验证过「还原成有 bug 的版本 → 测试确实会失败」，
> 避免写出永远通过的空断言。

### 识别成功了，但地图上的轨迹还是上一张的

这个坑比前面两个更隐蔽：**左栏数据全部是新图的**（置信度、轨迹点、里程、
路名都对），**只有地图是旧的**——轨迹线还在上一张截图的位置，
视野也停在上一片区域。

根因在腾讯地图 GL JS 的 `removeLayer`：

```js
// SDK 源码（压缩后）
i.removeLayer = function (t) {
  var e = this._layers[t];            // ← t 是图层 id 字符串
  e ? (e._setEventedParent(null), delete this._layers[t])
    : this._fire("error", { error: new Error("The layer '" + t + "' does not exist in map") });
}
```

而我们的代码传的是**图层对象**：

```js
map.removeLayer(polyline);   // ✗ polyline 是 MultiPolyline 实例
map.removeLayer(polyline.id) // ✓ 传 id
```

传对象 → 查不到 → 抛 `The layer '[object Object]' does not exist in map`
→ **异常中断 `drawMapInner`** → 后面 `lastPath = path` 没执行、
新轨迹也没画 → `fitBounds` 仍按旧路径定位视野。

外层 `drawMap` 的 catch 只 `console.error`，于是完全静默：
左栏照常更新（那部分在 `drawMap` 之前就渲染完了），地图却停在上一张。

实测证据（浏览器 console）：

```
Error: The layer '[object Object]' does not exist in map
    at i.removeLayer (gljs.js:69:395974)
    at drawMapInner (http://127.0.0.1:8848/:498:17)
```

修法：`removeLayer(layer.id)`。同时把图层清理包进 try/catch，
避免 SDK 行为变化时再次静默中断整段绘制。

> **教训**：这次的定位路径值得记住——
> ① 浏览器 console 里的报错指向 SDK 内部，就去翻 SDK 源码；
> ② 压缩代码里 `this._layers[t]` 这种形式直接说明了参数的语义；
> ③ 用一个只接受 id 的桩复现真实行为，测试就能抓住它
> （`tests/test_frontend.py` 的场景 6 就是这么写的）。

### 右侧的两个可视化面板：应该同时可见，而不是互斥切换

用户的预期一直是「**右侧上方是识别到图片，右侧下方是原始图**」——
两个都要看得到：地图用来确认位置对不对，原图用来确认轨迹有没有抠错。

历史上这里做成了「地图 / 原图叠加」两个**标签页互斥切换**。
识别完成后停在「地图」页，原图整个消失，用户反馈
「右侧下方原始的怎么都不显示了」——看起来像功能坏了。

改成上下堆叠、两个面板同时可见：

```html
<div class="vis-block">
  <div class="vis-title"><b>识别结果</b><span class="hint">腾讯底图 · GCJ-02</span></div>
  <div id="map"></div>
</div>
<div class="vis-block">
  <div class="vis-title"><b>原始截图</b><span class="hint">绿色为识别出的轨迹，黄色为锚点</span></div>
  <div id="preview"><img id="prevImg"><canvas id="prevCanvas"></canvas></div>
</div>
```

`switchTab()` 随之改为 `ensureMapReady()`：只负责「确保地图已创建、
尺寸正确、视野对准轨迹」，不再管显隐。

> **教训**：互斥切换看起来更"干净"，但它与用户的实际工作流冲突——
> 校验识别结果时，地图和原图是要**对照着看**的。
> 把两个东西藏进标签页，用户就得反复来回切。

## 路名归属差了好几公里：两个「想当然」的坑

用户反馈某张截图识别结果很差——路名归属完全对不上，
实际骑的是「水城路/虹桥路/古北路/红宝石路」，识别却给出「虹许路/中环路」，
整体偏了好几公里。

### 先排除一个误解：不是「缩放程度高」

实测全部样本，尺度越小反而越准：

| 尺度 m/px | 置信度 | 内点 | RMSE | 贴路后 |
|---|---|---|---|---|
| 0.221 | 0.791 | 4 | **8.6 m** | 2.3 m |
| 0.857 | 0.748 | **2** | **115.2 m** | 11.7 m |
| 4.083 | 0.885 | 4 | 96.8 m | 6.8 m |

尺度与精度无关。决定精度的是**有效内点数量**——
只有 2 个内点时配准几乎等于两点定线，RMSE 必然上百米。

### 坑一：词典里的短条目是 OCR 残片，坐标属于另一个地点

词典里有一条 `上海世` = `121.40071, 31.26275`——那是**上海西站**的坐标
（「上海西站」被 OCR 截断成「上海世」留下的残片）。

而 `Lexicon.lookup()` 的子串匹配规则是双向的
（`key in k` 或 `k in key` 都算命中），
于是查「上海世贸商城」时，「上海世」作为它的子串被命中，
返回了**上海西站**的坐标——偏离真实位置 **6.8 公里**。

而冷启动其实已经查到了正确坐标（121.40087, 31.20189），
却因为「词典已命中」被直接丢弃，根本没机会参与配准。

**修法**：子串匹配必须**分方向**：

| 方向 | 安全性 | 规则 |
|---|---|---|
| 查询名包含词典 key | 安全 | key ≥ 3 字即可 |
| 词典 key 包含查询名 | **危险** | 需 `len(key)/len(name) ≥ 0.6` |

「上海世」/「上海世贸商城」= 0.5 < 0.6 → 拦下。

### 坑二：冷启动的簇心过滤把正确候选扔了

冷启动的互证机制用**地理距离**判断区域。但**地理上更紧密 ≠ 方位正确**：

| 地名对 | 地理距离 | 像素 y | 真实纬度 |
|---|---|---|---|
| 虹桥基金小镇 ↔ 红松东路 | **791 m**（赢得簇心，错） | 2521 / 2122 | 31.1829 / 31.1875 |
| 上海世贸商城 ↔ 上海长风大悦城 | 2379 m（正确但被丢） | 1416 / 206 | 31.2019 / 31.2227 |

簇心被定到南边那片错误区域，随后按 1500m 阈值硬过滤时，
「上海世贸商城」（2399m）与「上海长风大悦城」（4471m）**被直接丢弃**——
而它们恰恰是唯一正确的两个。

**修法**：簇心过滤放宽为「**只排序、不丢弃**」，
挑选的正确性交给 RANSAC 的几何一致性。

### 修复效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 配准内点 | 2 | **3** |
| 配准残差 RMSE | 115.2 m | **11.7 m** |
| 精修后贴路中位 | 11.7 m | **4.0 m** |
| 路名归属 | 虹许路、中环路、华光路 | **安龙路、虹古路、水城路、虹桥路、古北路、红宝石路** |

> **教训**：当一个「预处理筛选」把正确候选过滤掉时，
> 先问「这个筛选比下游的算法更懂吗」。
> RANSAC 靠几何一致性判断哪一组候选自洽，距离启发式做不到这件事。
> 这类交互设计要问的是「用户想同时看到什么」，
> 而不是「怎么排版看起来整齐」。

## 多图模式：路线长时怎么截

**长路线一张截不下时，别硬凑**——沿路线滑动连拍几张，服务端自动拼。

### 什么时候用

| 截图类型 | 能定出「位置」 | 能定出「形状」 |
|---|---|---|
| 城市级（一张盖住全程）| ✅ 300-900 米 | ❌ **原理上不行** |
| 街道级（一张盖一段）| ❌ 尺度不稳 | ✅ 锯齿清晰 |
| **街道级多张拼接** | ✅ **13/21 米** | ✅ **偏差 4.0%** |

城市级截图里，11 公里的骑行只占约 680 像素——**底图上画的那条线本身就是直线**，
街道锯齿在截图阶段就丢了。路名能修正位置，但修不了形状。

### 怎么截

1. 在 App 里把地图放大到**能看到街道名**；
2. 沿路线滑动连续截图，**相邻两张留约 1/3 重叠**；
3. 一起选中上传（网页端支持多选）；
4. 看「拼接复核」分数与虚线框，确认拼对了再看轨迹。

> ⚠️ **最关键的一条：截图里必须有骑行轨迹线。**
>
> 地图 App 的骑行路线是**按需渲染**的——只有**骑行详情页**才画，
> 单纯在地图上浏览、平移时**不画**。
> 你截到的是纯地图（只有底图），那就没有轨迹可识别。
>
> 实测有人截了 4 张腾讯淡色底图的纯地图，
> 程序从底图**绿地**里「提取」出一条绿色三角形——
> 现在会明确报错「轨迹形状不合理，请确认截图里有骑行轨迹线」。
>
> 另外：**腾讯淡色底图比高德底图更容易误判**，
> 因为绿地饱和度低，正好落在轨迹线的取值区间里。

> **重叠要多少？** 实测下来要求很低：**街道级下 3% 重叠（约 24 像素）就能精确配准**
> （位移误差 0.0 像素）。1/3 是保守建议不是硬门槛——
> 街道级底图的特征足够密集。详见
> [`docs/HANDOVER.md` §22.21.10](docs/HANDOVER.md)。
>
> ⚠️ 但有个前提：两张图必须是**滑动时分别截的**（每次都会重新渲染）。
> 如果你是拿同一张图裁两半，重叠区像素完全相同，SIFT 会失效。

滑动截图中途那张**没有**起终点徽章是正常的
（只有第一张有「起」、最后一张有「终」），拼接后会自动对上。

**上传顺序无所谓**：服务端会自动找相邻关系，正序、倒序、乱序结果一致
（实测倒序上传画布 4177×3864，起终点坐标只差 1 像素）。
早期版本会因为「倒序时算出位移近 0 的假匹配」把含起点的图误当成重复删掉，
现在判重只认**内容一致**的两张图，0 位移假解已在配准阶段直接排除。

**拆得更细也支持**：实测同一条路线拆成 **12 张**，画布 9896×6694
（6625 万像素）仍能拼出完整轨迹，复核分 1.0。
细截图之间难免有空洞 / 1-3 像素错位，轨迹线会在接缝处断成两段，
服务端会依据起终点徽章自动补一段短直线把缝接上，不影响里程估计。
所以「图之间有 N% 的空洞」只是提示覆盖不足，不代表拼接失败。

### 怎么确认拼对了

页面上会给两个依据：

- **拼接复核**：把每张图按算出的变换贴回画布逐像素比对，
  给出相似度（实测 0.952）。低于 0.9 会明确提示「接缝可能没对齐」。
- **黄色虚线框**：标出每张原图在画布上的位置并编号。
  框应当首尾相接、彼此略有重叠；哪个框飘到一边就是那张没对上图。

还有两种常见情况服务端会主动提示：

| 提示 | 含义 | 怎么办 |
|---|---|---|
| 「第 X、Y 张是同一视角的重复」 | 同一张图传了两次 | 只传一张 |
| 「图 X↔图 Y 位移近 0 但内容不同，判为错配并断开」 | 两张不同区域的图配出了假匹配 | 正常，服务端已自动断开，不用处理 |
| 「图之间有 N% 的空洞」 | 滑动步子太大，中间漏了区域 | 步子小一点，多截几张 |

> 画布上灰白色的区域表示**那里没有图**（几何上就是空隙，不是拼错了）。
> 拼接图的外侧空白会自动裁掉。

### 接口

```bash
curl -X POST http://127.0.0.1:8848/api/recognize_multi \
  -F "files=@shot1.jpg" -F "files=@shot2.jpg" -F "files=@shot3.jpg" \
  -F "city=上海"
```

返回里多一个 `stitch` 字段：

```json
{
  "stitch": {
    "ok": true,
    "used": [0, 1, 2],
    "canvas_size": [828, 1024],
    "verify_score": 0.9515,
    "verify": [{"index": 0, "similarity": 1.0, "pixels": 194560}],
    "links": [{"i": 0, "j": 1, "inliers": 863, "ncc": 0.9414, "tx": -190.0}]
  }
}
```

### 拼接方式可切换（A/B 对比）

页面上的「多图拼接方式」下拉提供三种后端，接口用 `stitch_backend` 指定：

| 后端 id | 含义 | 依赖大模型 |
|---|---|---|
| `sift`（默认） | 逐对全组合 SIFT + RANSAC + 候选峰 NCC，按 `inliers×ncc` 选最大生成树 | 否 |
| `llm` | 多模态模型直接判断图间相邻关系与相对位移，**跳过 SIFT**（纯语义粗配准） | 是 |
| `llm_guided` | 模型只圈定候选图对，变换矩阵仍由 SIFT 精配准 | 是 |

三种后端只在「边的来源」上分叉，之后的连通块、位姿树、贴图、
逐像素复核、徽章守恒是同一套代码，所以 `verify_score`、
`canvas_size`、`used`、`badge_conservation` 可以直接横向比较。

🔴 **提示词 v2 要求模型先「识别一条链」**：`llm` / `llm_guided` 共用
`trajectory-chain-v2`，要求模型把轨迹线的出边↔入边接续当作**唯一主证据**、
禁止只凭同名道路 / POI 判相邻；先输出 `order`（1..n 的排列，即沿轨迹的
真实先后），再只输出相邻两图的边，位移主导轴必须同号，每条边必填
`evidence`。结果卡片会显示「识别顺序」「链条完整 / 不完整（N 块）」
「方向冲突 N 条」以及前两条轨迹接续依据；`backend_diagnostics` 里对应
`order` / `chain_complete` / `connected_components` / `missing_images` /
`direction_conflicts` / `prompt_version`。`llm_guided` 还会把 `order` 的
相邻图对补齐交给 SIFT 验证，避免模型只给几条边导致图永远连不全。

只想测「识别」这一步，建议按 `llm_guided` → `llm` 的顺序：前者把顺序
识别交给模型、像素级变换仍由 SIFT 给；后者连位移也由模型估，两次结果
相减就能分离「顺序识别误差」与「坐标估计误差」。

🔴 **v3 补上垂直位移**：11:05 实测纯 VLM 画布 **6854×2910 ≈ 单图高 2720**，
而 SIFT 基线 **6423×3373** 多出 **653px 累积垂直漂移**——模型把斜向滑动
当成纯水平平移、`dy_ratio` 全填 0，轨迹线在每张图接缝处断开，
`track_points=0`、`掩膜为空`。v3 要求按重叠区同一地物的上下错位估
`dy_ratio`（典型 0.02~0.15，符号沿链一致），诊断给出 `dy_values` /
`dy_zero_count` / `dy_all_zero`，结果卡片显示「垂直位移全为 0（接缝可能错位）」。

⚠️ 提示词只能让模型**尝试**给非零垂直位移，压不到像素级精度。要让接缝
真正对齐，请选 `llm_guided`（顺序仍由模型识别，变换由 SIFT 求）；纯 VLM
是用来量化差距的，不是承诺可用结果。

大模型后端复用已有的可选配置（`.env`，保存后自行重启服务）：

```dotenv
LLM_BASE_URL=https://your-endpoint/v1
LLM_API_KEY=sk-xxxx
LLM_MODEL=gpt-4o-mini
LLM_TIMEOUT=600
```

🔴 **请求必须用流式**：`app/llm.py` 固定发 `stream=True` 并解析 SSE，
`LLM_TIMEOUT` 默认 600 秒（10 分钟）。这是 2026-11-13
实测出来的：推理型模型跑 7 张图约需 **59~95 秒**（`reasoning_tokens=2668`），
非流式请求会被中转网关在约 30 秒掐断（`HTTP 102` 空响应），
`max_tokens=1200` 则会在思考阶段就被截断、拿不到 JSON。
响应里的 `reasoning_content` 会被丢弃，只拼 `content` 分片。
模型名请填写**实测能出结果**的那个：带 `chat_template_kwargs.thinking=true`
的高配模型在同样的 7 图任务上跑满 600 秒仍只有 reasoning、没有答案。

🔴 **`max_tokens` 有端点硬上限 65536**：实测填 512000 会立刻返回
`HTTP 400 invalid_parameter`（`Field 'max_tokens' must be at most 65536`），
纯 VLM 后端每次都失败。请求体用
`min(DEFAULT_MAX_TOKENS, MAX_TOKENS_CEILING)` 做运行时钳制——即使本地把
常量手动调大也不会再触发这个错误。默认值 65536；实测 16384 对 7 图任务
已经够用，调大不会更准，只会让模型有空间输出更长。

`GET /api/stitch-backends` 返回各后端是否可用与不可用原因；未配置时
前端禁用对应选项。选了不可用后端**不会**静默改用 SIFT——结果里会给
`stitch.ok=false` + `backend_error=true` 并写明原因，避免污染对比数据。

```bash
curl -X POST http://127.0.0.1:8848/api/recognize_multi \
  -F "files=@shot1.jpg" -F "files=@shot2.jpg" \
  -F "city=上海" -F "stitch_backend=llm"
```

⚠️ 纯大模型模式没做几何配准，`links[].inliers` 恒为 0 是正常值，
位姿树改用 `weight`（模型置信度）选边。判断拼得好不好请看
`verify_score`，不要拿内点数与 SIFT 直接比较。按设计它大概率明显
低于 SIFT——这个模式是用来**量化差距**的，不是承诺更高准确率。

## 三个最容易踩的坑

### ① 道路名不能作锚点（最严重）

地图把路名**沿道路/河流走向排布**，文字中心不对应任何固定地理位置。
实测同一张图上：

| 锚点类型 | 真值反投影偏移中位 | 最大 |
|---|---|---|
| POI 类（公园/宾馆/广场/车站） | **32 px**（≈170 m） | 192 px |
| 道路类（大渡河路/祁连山南路/桃浦河…） | **458 px**（≈2.5 km） | 1637 px |

早期版本把道路名也当锚点，结果**整体平移 3 公里**。而 RMSE 完全看不出来
（RMSE 只反映锚点之间的自洽性，不反映绝对位置）。

**对策**：
- 竖排文字几乎必然是道路名，直接排除
- 词典只收录 POI 类条目
- 加**绝对位置自校验**：把内点锚点的真值反投影回像素，若不落在它自己
  文字附近就告警并降低置信度。这个检查能自动抓住「坐标对错同名地点」

### ② GeoJSON 的坐标顺序与方向

- **坐标系**：腾讯/高德底图是 GCJ-02，比 WGS-84 多约 350 米偏移。
  把 WGS-84 坐标直接画在腾讯底图上会整体偏 350 米。
  接口同时返回 `geojson`（WGS-84）和 `geojson_gcj02` 两份，前端用后者。
- **方向**：GeoJSON 的 LineString 坐标顺序即绘制顺序，本项目保证
  **第一个点是起点、最后一点是终点**，并在 `properties` 里显式声明
  `direction: first_point_is_start`。很多第三方工具默认「首点=起点」
  来标注起终点，顺序反了地图上就会画反。

### ③ 校验要选独立参照

「反投影回截图后与原轨迹吻合」只证明**自洽**，不证明**位置正确**。
绝对精度必须用第三方数据（真实路网）验证：
轨迹贴在路上只能说明它走在某条路上，不能说明是哪条。

### ④ `warpPerspective` / `warpAffine` 的矩阵方向

这两个函数**默认把 M 当作 src→dst 直接使用**。传反了不会报错，
只会**内容整体错位**，而且画面「看起来」还行（重叠度高，肉眼难辨）。

实测踩过：A 图左上角的标记（src x=25）应落在画布 x=491，
实际落在 x=983 —— **差 507 像素**，接缝处其实没对上。

**怎么验**（别靠看图）：

```python
src = np.zeros((100,100,3), np.uint8); src[10:40,10:40] = (255,0,0)
T = np.array([[1,0,200],[0,1,0],[0,0,1]], float)
cv2.warpPerspective(src, T, (400,100))
# 标记应落在 x=225 附近
```

**对策**：几何变换类代码要有「已知标记反推落点」的回归测试。
本项目现在这条测试在 `tests/test_multishot.py` 里，
方向反了会差 500+ 像素，立刻暴露。

### ⑤ RANSAC 会被静止 UI 骗

拼接多张截图时，App 的状态栏、右侧按钮、底部卡片在每张里**位置完全相同**，
它们提供大量「位移=0」的对应。而**单位变换本身也是合法的相似变换**，
于是「内点最多」的准则会被 UI 骗过去。

实测：UI 对应 58 对 vs 地图内点 64 个——**只差 6 个，UI 一多就翻车**。

**对策**：不靠猜 App 布局，靠一个事实——
**静止 UI 在两张图的同一像素位置内容完全相同**，
而地图内容即使重叠、在同一像素位置也不同（那是不同的世界位置）。
把「同位置内容相同」的区域从特征匹配里剔除即可。

### ⑥ 底图的重复纹理让 RANSAC 选错解（最隐蔽）

城市街道网格规则，底图里有大量**周期性重复结构**。
实测（上海街区、两图重叠 240px）：

| 解 | 匹配数 |
|---|---|
| 真解 `dx=-560` | 393 |
| 假解 `dx=+449` | **509**（更多！）|

RANSAC 选内点最多的，于是选了假解——**位移误差 1024 像素，完全拼错**。

⚠️ **光靠 NCC 也救不了**：用假解算出的 NCC 是 0.9987——
因为 NCC 是拿「RANSAC 选出的变换」去比，数学上自洽、语义上却错。

**对策**：从**位移直方图**里找出几个候选峰，**逐个算 NCC，取最高的**。
实测真解 NCC=1.0000、假解 0.1866。

**通用教训**：这类错误**不报错、只静默拼错**。
必须靠「已知真值 + 位移误差」来验，光看接口返回 200 没用。

### ⑦ 形状判据在「单图」和「拼接画布」上含义不同

判轨迹线是不是「底图色块」时，最自然的两个判据都不可靠：

| 判据 | 真实轨迹 | 绿地误判 | 能区分吗 |
|---|---|---|---|
| 宽度 ≥ 图宽 75% | **96%**（误触发） | 91%（触发） | ❌ |
| 骨架填充率 > 0.45 | 0.0008 | **0.0022** | ❌ |

- 第一条错在**呈现形式变了**：单图里轨迹线不会横跨整幅图，
  但 11 公里的路线**本来就该**横跨整张拼接画布。
- 第二条错在**误判对象不是实心块**：被误抓的绿地是**沿河绿地边界**，
  同样是细长的，填充率甚至比真实轨迹还高。

实测真实轨迹在拼接画布上的框宽是 **4016 / 4178 = 96%**——
正好被第一条判死，于是用户明明截到了起终点，
却被告知「未检测到起点徽章」「请确认截图里有骑行轨迹线」。

**对策：用拓扑当主导信号。**
真正的骑行轨迹**一定同时贴着「起」和「终」两个徽章**，底图元素不会。
实测真实轨迹的拓扑距离只有 **39 像素**；而绿地误判样本压根没有起点徽章
（它那个「终点」是右上角的红色 UI 元素）。

```python
topo_ok = 有起终点徽章 and (包围盒到两徽章距离之和) < scale.topo_dist
if not topo_ok and (宽度可疑 or 形状可疑):
    判为底图元素
```

**通用教训**：
1. **选判据时先问：它依赖的是呈现形式，还是内容语义？**
   依赖呈现形式的判据（宽度、比例）在场景变了之后会**反向失效**。
2. **更严格的阈值 ≠ 更可靠的判据**。要么两个独立信号同时成立，
   要么就用不依赖呈现形式的那个。
3. **报错文案不能误导**。原来不管哪种失败都说「请确认截图里有轨迹线」——
   而用户明明截到了。现在按「有没有徽章」分流。
4. **阈值本身也别写死**：上面那个 `topo_dist` 由画布对角线推导，
   见下一节。

### ⑧ 所有像素阈值都要有「标尺」

前面几个坑陆续修完后，代码里留下了一串
`260 / 400 / 500 / 600 / 700 / 800 / 9px / 1.2 亿像素上限`——
每一个都是当时针对某一批截图调出来的。换个分辨率或换个张数，
链路就会在某一个阈值处断掉。用户一句话点破了问题：
**「你应该改通用的结构，不要针对我传的图片定制化设置」**。

根因是**把两类尺度混为一谈**：

| 尺度 | 标尺 | 随什么变 | 决定哪些阈值 |
|---|---|---|---|
| 画布尺度 | 对角线 / 短边 | 拼接张数、画布大小 | 包围盒粗筛、拓扑距离、补缝容差、画布内存上限 |
| 内容尺度 | 徽章直径 → 轨迹线宽 | 单张截图的缩放级别 | 贴合容差、面积下限、形态学核、补线宽度、0 位移容差 |

12 张拼出的画布再大，徽章仍是几十像素、轨迹线仍是 10 像素左右。
用画布尺寸去量内容，或固定一个数字不管画布多大，都会错。

现在统一由 `src/app/scale.py` 的 `Scale` 派生，业务代码里不再出现裸像素数字：

```python
scale  = Scale.from_image(img, badge_d)   # badge_d 从检出的徽章连通域反推
touch  = scale.touch_dist                 # 徽章直径 × 3
kernel = scale.close_kernel               # 轨迹线宽 × 1.1，取奇数
gap    = scale.bridge_gap(start, end)     # 路线跨度 × 8%，受内容尺度上下界约束
budget = canvas_pixel_budget(总输入像素)   # 内存预算 ∩ 输入规模
```

`tests/test_scale.py` 锁住两条性质：**内容阈值不随画布变化、
画布阈值不随徽章变化**；并把同一批真实截图整体缩到 0.85 倍再跑一遍，
验证不是只对某个分辨率有效（0.85 / 1.0 / 1.25 倍均识别成功）。

> 仍然保留的配置项：`VisionConfig.badge_min_area / badge_max_area`
> 是按目标 App 的 UI 元素尺寸设定的**检测范围**，属于业务配置而非
> 散落的魔法数；换设备像素密度时应在此调整，不要改业务代码。

## 五个阶段

```
截图
 ├─ ① 轨迹提取   色彩分割 → 形态学 → 连通域 → 骨架化 → 图路径追踪
 ├─ ② OCR        RapidOCR（支持竖排/旋转文字）→ 锚点候选
 ├─ ③ 地理编码   四级：用户确认 > 在线服务（高德/腾讯/百度/天地图）
 │                > 本地词典 > OSM 冷启动
 ├─ ④ 配准       RANSAC + north_up 模型 → 像素→墨卡托变换矩阵
 │                + 绝对位置自校验 + 路网约束精修
 └─ ⑤ 反投影     折线 → 经纬度 → GeoJSON（WGS-84 + GCJ-02 两份）
```

### ① 轨迹提取

轨迹线是「深色描边 + 浅灰填充」的双层结构，不能用暗阈值直接提取。用
**低饱和 + 中等亮度** 的掩膜：地图底色是蓝灰（饱和度高）被排除；文字笔画虽暗
但只有 2-3 px 宽，而轨迹线宽 8-10 px，靠开运算分离。

起终点用 HSV 找大色块（绿色「起」、红色「终」）。面积阈值是关键：徽章约
4000+ 像素，而虚线碎片只有 100-300，相差一个数量级。红色虚线（规划路线）
饱和度高，被饱和度条件天然排除。

骨架化后**在 8 邻接图上用 Dijkstra 搜索起→终路径**，而不是按投影排序。
原因见下方「踩过的坑」。

### ② OCR 与锚点分级

| 类型 | 例子 | 锚点价值 |
|---|---|---|
| icon | 带图标的 POI | 最优，图标锚点即真实位置，误差 2-3 px |
| poi | 上海动物园、西郊宾馆 | 好，文字中心偏移 7-28 px（35-150 m） |
| road | 曹安公路、大渡河路 | **不作为锚点**，只做区域校验 |

道路名的反投影偏移比 POI 大一个数量级（详见「三个最容易踩的坑」①）。

### ③ 地理编码

四级优先级，越靠前越可信：

1. **用户确认** — 网页上点过地图纠正的地名，最高优先级
2. **在线服务** — 按已配置的密钥自动选择高德 / 腾讯 / 百度 / 天地图。
   这些与美团底图同源，POI 坐标没有基准偏差
3. **本地词典** `data/lexicon.json` — 离线可用，精度受限于种子来源
4. **OSM 冷启动** `src/app/coldstart.py` — 前三级都没命中时的最后一道网

返回多个候选时全部交给 RANSAC，由几何一致性挑选，天然处理同名地点歧义。

**天地图的三个注意点**：一是 tk 只认环境变量 `TIANDITU_API_KEY`（单一变量名），
`/api/health` 会主动探测 tk 是否真的可用；二是天地图返回 CGCS2000
（工程精度上等同 WGS-84），而项目内部锚点按 GCJ-02 处理；坐标换算统一由
`src/app/maps/contracts.py::to_gcj02` 按 provider 声明的 `output_crs` 完成——
漏掉会整体偏约 570 米；
三是普通搜索是「包含关键词」语义，项目只保留同名候选，并从词典里该城市
的已核验坐标派生搜索视野，过滤异地同名（详见 HANDOVER §22.28）。

**在线源的调用语义是「单源严格模式」**：配了哪家就用哪家，失败**直接提示**，
不自动换到另一家。

- `MAP_GEOCODING_ORDER=tianditu` → 只用天地图，它失败就在识别结果里提示原因；
- `MAP_GEOCODING_ORDER=amap,tianditu` → 显式声明多源，此时才启用依次回退；
- **不配** → 用默认顺序里第一个有 key 的源（当前是高德），同样失败不换源。

改这个值不需要重启服务（`.env` 每次读取）。顺序只由 `MAP_GEOCODING_ORDER` 这一个环境变量决定。

> ⚠️ 早期版本是「高德失败就静默落天地图」。实测高德当日配额用尽
> （`USER_DAILY_QUERY_OVER_LIMIT`）时，每个地名都先打高德再打天地图——
> 既慢一倍，又让人误判实际用的是哪家。现在失败原因会写进识别结果的提示里，
> 例如「在线地理编码不可用，已降级到本地词典与 OSM 冷启动：amap: 高德
> USER_DAILY_QUERY_OVER_LIMIT」。

**为什么需要第 4 级（冷启动）**

第 3 级只覆盖已核验过的地名。换一个区域就完全无法识别：实测长宁剑河路
一带，OCR 明明读出了「安龙小区」「新安小区」「珍宝公寓」「长宁实验小学」
这些真实地名，却因为「词典里没有、也没配密钥」而拿到 0 个坐标，配准直接失败。

冷启动按城市限定范围去 OSM 检索这些地名。这与本项目既有做法一致——
`src/app/seed_lexicon.py` 的初始词典种子本来就是「viewbox 限定的地理编码查询」
得到的。检索结果标记为 `osm` 源（权重低于用户确认与在线服务），
并写回词典形成数据飞轮；它的 100-300 米基准偏差由第 ④.5 步的路网精修纠正。

**冷启动的三阶段策略**（`src/app/coldstart.py`）

早期版本「要求完全同名 + 城市级 viewbox」，在浦东实测**6 个 POI 全部 0 命中**。
三个原因分别对应三个阶段：

*阶段一 · 多查询变体* — Nominatim 的索引对前缀敏感，同一个 POI 换个写法
结果就不同：

| 查询 | 结果数 |
|---|---|
| `进才实验中学 上海` | 0 |
| `上海市进才实验中学` | 1 ✓ |

所以每个地名用多个变体检索：`{名} {市}`、`{市}{名}`、`{短名}{名}`、`{名}`。

*阶段二 · 名称相似度* — OCR 会截断地名，不能要求完全同名：

| OCR | OSM 实际名称 | 相似度 |
|---|---|---|
| 进才实验中学 | 上海市进才实验中学 | 0.92 ✓ |
| 水清木华 | 水清木华公寓 | 0.92 ✓ |
| 乡土田园区 | 何文田上海水配水庫 | 0.08 ✗ |

低于 0.55 直接丢弃。用 Jaccard 字符相似度 + 子串加权。

*阶段三 · 多锚点互证* — 单个地名无法自证位置：「花园2期」能匹配到
朗香/星宇/尼德兰/三湘盛世四个不同小区的「2期」，取哪个都可能错。

但**多个独立检索的地名若彼此落在 800 米内**，那这片区域就是真的。
实测浦东一例：华丽家族花园、天安花园、当代清水园、水清木华公寓
四个地名各自独立检索，命中点互相都在 300-500 米内，由此锁定区域中心
`(121.5537, 31.2282)`，再用它过滤掉其余候选——包括那个在安徽的
「水清木华」（同名异地，距离 164 公里）。

这一步**必须批量做**。单锚点无法自证位置，所以 pipeline 里冷启动是
一次性把所有未命中的地名交给 `lookup_many()`，而不是逐个 `geocode()`。

**OSM 检索限速**：Nominatim 使用政策要求最多 1 次/秒，因此冷启动逐个查询，
且查到足够候选就停。结果带磁盘缓存（`data/cache/coldstart.json`），
同一区域再次识别几乎不花时间。

> **一个教训**：viewbox 只是 Nominatim 的**排序提示**，不是强制过滤。
> 对「上海市」这种大范围 bbox 几乎不起作用——同名异地地点照样返回。
> 真正起过滤作用的是自己实现的距离约束与互证。

### ④ 配准

墨卡托投影是保角投影，图像 y 轴向下、墨卡托 y 轴向上，故像素→墨卡托的正北
模型是 `M = [[s, 0], [0, -s]]`，只有 2 个自由度，对锚点噪声极不敏感。

按自由度从低到高依次尝试，优先选精度高的：

1. `north_up` — 正北朝上，2 自由度。默认地图状态，精度最高
2. `similarity` — 允许旋转，4 自由度。适配用户旋转过截图
3. `affine` — 一般仿射，6 自由度。兜底

### ⑤ 坐标系

内部统一 GCJ-02（与截图底图一致），输出可选 WGS-84 或 GCJ-02。
两者在中国境内差约 300-400 m，混用会导致轨迹整体错位数百米。

---

## 坐标系要点

```python
from app.geo.coords import wgs84_to_gcj02, gcj02_to_wgs84

gcj = wgs84_to_gcj02(lon, lat)   # WGS-84 → GCJ-02
wgs = gcj02_to_wgs84(lon, lat)   # GCJ-02 → WGS-84（不动点迭代，精确可逆）
```

`gcj02_to_wgs84` 用不动点迭代求解（GCJ 偏移量依赖原始 WGS 坐标，是隐式方程）。
一步近似会让 GCJ→WGS→GCJ 往返平移 347 m。

另注意：墨卡托尺度 ≠ 地面尺度。地面距离 = 墨卡托距离 × cos(纬度)，
上海一带差 15%。里程用 haversine 计算，不要用「像素长 × 比例尺」估算。

## 「越用越准」的数据飞轮

```
用户上传截图 → 识别 → 地图叠加展示 → 用户确认/纠正锚点
      ↑                                        ↓
      └────── 本地词典（地名词 → 精确坐标）←──┘
```

每次纠正都会强化 `data/lexicon.json` 中对应地名的坐标权重。这类「随使用量
积累」的资产现在有两种：地名词典（**地名 → 点**）与轨迹模板
（**形状 → 像素/地理对应**，见后文）。算法侧的边际收益递减很快，数据侧几乎不衰减。

四个资产的区别：

- **地名词典**：`(城市, 地名) → [经纬度候选 + 权重]`。无限增长，是护城河；
  但只在「同一个地名再次出现」时生效，帮不了没有地名的概览图
- **轨迹模板**：`(像素折线 ↔ 地理折线)`，按弧长一一对应。让同类轨迹复用
  历史变换，是「只放一张高缩放图也能识别」的前提（见下节）。P2 起按
  `shape_domain` 区分 `overview` / `detail`：**只有「概览单图 + 可选多图」
  配对注册才新增 overview 模板**，普通识别沉淀的 detail 模板不参与概览图
  定位，避免跨缩放假阳性
- **视觉锚点模板**：图标+文字+像素偏移。有天花板（该城市标注种类有限）
- **评估样本**：`(截图, 真值)` 二元组。价值在于回归测试，不用于训练

冷启动城市没有词典时，靠在线地理编码兜底，但通用 API 对冷门地名覆盖很差。
这时置信度会降低，前端应主动请用户配合，而不是假装很准。

### 数据飞轮的防毒门槛（否则「越用越偏」）

在线地理编码 / 冷启动发生在配准**之前**，那时还不知道这次识别准不准。
若低置信度的错误结果也照单全收，坐标会一次次加权，下次再用同名候选时
它权重最高 —— 错误被自我强化。`src/app/lexicon_guard.py` 因此规定：

| 写入来源 | 规则 |
|---|---|
| 用户显式纠正 `/api/feedback` | 立即写入，`verified=true`，解除权重上限 |
| 在线源 / OSM 自动沉淀 | 先排队，等 `pipeline.run()` 算出最终置信度后统一裁决 |
| 自动写入的否决条件 | 置信度 < 0.35、低信息量直线输入、截图里程与几何里程量级不符、锚点残差系统性同向、与已核验异源条目相距 200 m~10 km |
| 自动写入的上限 | 未核验条目 `weight ≤ 3.0`，`lookup().quality = weight/5` 永远 < 1.0 |

门槛**只看独立证据**，不用贴路距离/锚点残差——它们在假解上也会变好。
`diagnostics.lexicon_write_guard` 给出本轮 `pending / written / rejected`
和每种拒因的计数；`stats()` 新增 `verified_points / auto_points`。
非流水线调用（没有最终置信度）仍可冷启动，但 boost 压到 0.2 且同样封顶。

### 纠正入口的可见反馈（2026-11-11）

以前点「锚点明细 → 纠正」后，提示只放在**左栏**的 `correctBox` / 状态栏，
而 `startCorrect()` 会把页面滚动到右侧地图，左栏被滚出视野；地图点击后
也只有左栏一行状态文字，用户看不出这一下是否生效。现在提示改成
**地图内的浮层**（`#mapHint`，跟随 `#mapShell` 一起滚动）：

- 进入纠正模式：地图加紫色描边 + 十字光标，浮层显示「请在地图上单击
  「X」的正确位置」，并说明单击即保存、点「取消」可退出；
- 单击地图：第一时间在点击处落一个临时标记（适配层 `showPin/clearPin`，
  腾讯/高德都支持），浮层切成「正在保存…」并显示 GCJ-02 坐标；
- 请求返回：成功显示「已记录 + 坐标 + 词典条目数 + 下次识别生效」和
  「完成」按钮；失败显示错误并保留纠正模式，可直接在地图上再点一次重试。

提交语义不变：仍是「先点按钮、再点一次地图」，`/api/feedback` 写入
`verified=true` 点位，本次轨迹不重算，下次识别才生效。详见交接文档 §22.46。

### 人工纠正清单与一键回滚（2026-11-11）

🔴 **纠正不是越多越准**。用户点位在 `Geocoder.geocode()` 里会**短路**掉在线
地理编码（`geocode.py` 第 1 步 `lookup_by_source(..., ("user",))` 命中即返回），
一条点错的纠正会长期生效，且天地图的正确坐标再也不会进入候选池；
`evaluate_write()` 对 `source="user"` 直接放行 `user_verified`，连异源冲突
检查都不做。同一地名第二次点错只是**再新增**一条 `weight=2.0` 的点位，
旧点不会消失。收益则很快饱和：同坐标 `boost=2.0`，
`quality = min(1, weight/5)` 第 3 次就到 1.0，之后重复提交没有任何区别。

因此左栏新增独立的**人工纠正**卡片（在「锚点明细」下方，但**不嵌进**默认
隐藏的 `anchorCard`——否则页面刚打开、还没识别时就看不到回滚入口），
把判断依据与退路都摆到明面上：

| 列 | 含义 |
|---|---|
| 名称 / 坐标 / 权重·次数 | 词典里的归一化 key、GCJ-02 点、`weight / count` |
| 本次识别 | `已用作内点`（本次 `anchors_used` 命中）/ `本次未采纳`（落在 `anchors_rejected`）/ `本次未出现` |
| 风险 | 名称 ≤3 字或含 UI 文案 → `疑似 OCR 残片`；同一 key 有多条 user 点 → `多个坐标（纠错过）` |

**怎么判断纠正准不准**：纠正后重新识别**同一张图**，若该地名出现在「内点」
且内点数 / RMSE 没有变差，说明这次点被采纳且自洽；若落入「离群」或整体
指标变差，就是点偏了。手点坐标只有缩放级别精度（几十米），比在线地理编码
的门牌级坐标差，不要用它微调本来就正确的点。

点错时点「清空全部纠正」（二次确认）→ `POST /api/feedback/reset`：

- 只删 `verified=true` 或 `source="user"` 的点位，**保留自动写入的点位**，
  空 key 一并删除；内存与磁盘同步更新，**不需要重启服务**；
- 需要显式 `{"confirm": true}`，否则返回 400；没有人工点位时幂等返回计数 0；
- ⚠️ 无法完整还原：用户在**同一坐标**上纠正时 `_commit()` 会把原自动条目
  就地升级为 `user / verified`，原自动证据不另存，这类点位只能一并删除。
  返回值 `upgraded_auto_points_lost` 如实计数，前端提示里也会写明。
- 清空后该城市回到纯自动证据重新积累；轨迹模板库**不受影响**。

详见交接文档 §22.47。

## 轨迹模板：同类轨迹的复用（P0）

`/api/recognize_multi` 新增可选 `overview` 字段，用来上传「原始概览单图」：
缩放等级高、盖住整条路线、地名看不清。它**不参与 SIFT 拼接**——与街道级
细节图尺度差一个量级，混进 `files` 会让拼接失败甚至触发「退回第 1 张」；
服务端单独保存，返回 `overview_url` 与 `stitch.overview_present`。
也可用 curl 直接传：

```
curl -F "files=@shot1.jpg" -F "files=@shot2.jpg" \
     -F "overview=@whole_route.jpg" \
     -F "city=上海" http://127.0.0.1:8848/api/recognize_multi
```

每次成功识别（单图 / 多图）还会把这一轮的「像素折线 ↔ GCJ-02 地理折线」
沉淀到 `data/route_templates.json`（含真实位置，已加入 `.gitignore`）：

| 字段 | 含义 |
|---|---|
| `px_points` / `geo_points` | 各 64 点，按**弧长参数一一对应**；形状对齐后可直接插值出坐标，不必理解配准矩阵格式 |
| `shape` / `signature` | 归一化形状与 16 段有序方向签名 |
| `confidence` / `verified` / `hit_count` | 写入裁决、人工核验与命中累计 |

写入门槛与词典同源：复用 `_result_is_self_consistent` 的四项一票否决 +
置信度 ≥ 0.35 + 输入信息量；形状几乎相同的轨迹不新增条目，只累加
`hit_count` 并在置信度更高时刷新坐标。`GET /api/health` 的 `templates`
可查模板数量。接口响应多一个 `template_capture` 审计字段。

**「同类但不完全一样」能不能支持？** 能，但靠局部匹配，不是整条折线比对：

| 情形 | 结论 | 机制 |
|---|---|---|
| 缩放 / 裁切 / 平移不同 | 能 | 弧长重采样 + bbox 对角归一化 |
| 同一路线反着骑 | 能 | 反向变体 |
| 只截中间一段、或新图多绕一段 | 能 | 连续子段滑窗 + `coverage` 覆盖度 |
| 不同路线、只截一小块碎片 | 拒识 | 有序方向签名 + 覆盖度双重门槛 |

**P0 边界：只沉淀与判定，不产出坐标、不改变识别结果**。城市级全域形状搜索
已被证明不可行（交接文档 §21.4：前 12 候选分数差 0.1%，位置差 900-1600 m），
匹配严格限定在已沉淀模板集合内。验证：`tests/test_route_template.py` 24 项；
全量 pytest（Python 3.11）**407 passed / 2 warnings**。

## 概览图的参考级定位（P1）

P1 让「只放一张高缩放概览图」也能出坐标。但实测两张真实概览图
（1260×2720，同一条路线的往返）后发现，**原先的两个假设都不成立**：

| 原假设 | 实测 |
|---|---|
| zoom out 会把轨迹压成粗线、提不出形状 | 轨迹提取 **872 / 829 点**、confidence 0.95，起终点徽章与拓扑校验全过 |
| OCR 为空 → 无锚点 → 早退 | OCR 有 **42 / 46 条**，但几乎全是行政区、地铁线号、高架与大 POI，街道级路名仅 1 条；标注位置与真实点位差 0.8-16 km |
| 细节图形状与概览图差太远、匹配不上 | 反而**太容易匹配上**：一条 2 km 的扁长直线与十几公里的概览图 residual 仅 0.0438、signature 0.3873，被判成同类 |

所以做法改成 `src/app/template_fallback.py` + `pipeline.py` 阶段 2.5：

1. **前置判据**（只用 OCR 文本，在在线地理编码**之前**）：文本 ≥10 条、
   宽泛地名 ≥6 条且占比 ≥35%、街道级路名 ≤2 条、用户未手填路名 → 判为概览图。
2. **先试模板**：`TemplateStore.locate()` 命中才「直跳」并返回参考级结果；
   **未命中就回落原流程**，行为与改动前一致（不注入模板库时整条通道关闭）。
3. **参考级结果的约束**：confidence 封顶 **0.45**（实测样例 0.414）、
   `source="template"`、GeoJSON `quality="reference_only_unverified"`、
   warnings 明确「未核验、仅供轮廓参考」；不写词典、不触发后台精修、
   不再沉淀成模板（避免错误自我强化）。

拒识门槛比 P0 更严：新图与模板**两侧**都要有足够形状信息（直线度 ≥0.80
且 bbox 长宽比 ≥4 的扁长直线一律禁用，正是上表第三个假阳性的来源）；
模板地理里程须在 100 m–200 km；`template_in_query` 模式要求 coverage ≥0.85
（子段外只夹到端点，绝不外推坐标）。

形状命中后按弧长把当前图 64 点映射到模板 GCJ-02 折线：`ShapeMatch.mode`
区分「新图落在模板子段」与「模板落在新图子段」，`reversed` 保证 GeoJSON
首点仍是起点。往返实测：图9 命中图8 模板，`reversed=true`、residual 0.0670、
coverage 0.9844，产出 64 点坐标且方向正确；拿那条扁长直线模板去查概览图
则返回 `None`。

🔴 **冷启动仍然存在**：`data/route_templates.json` 为空时概览图只能回落
原流程。必须先有若干次含街道名的成功识别沉淀模板，之后才逐渐生效。

验证：`tests/test_template_fallback.py` 19 项 + `tests/test_route_template.py`
24 项；全量 pytest（Python 3.11）**426 passed / 2 warnings**，无回归。

## 双上传入口与配对注册（P2）

P1 留下的根因是**模板形状域混用**：模板的 `px_polyline` 来自细节图/拼接画布，
而 `locate()` 的查询永远是概览图。实测拿 3.7 km 的北新泾局部模板查十几公里的
概览图，`residual=0.054`、`coverage=0.86` 仍会命中——不同路线被判成同类。
`shape_has_enough_info()` 只挡住长宽比 ≥4 的极端扁长直线，挡不住一般细长曲线。

P2 把上传语义反过来：**概览单图是主入口，多图只在缩放过高时补传一次**。

| 入口 | 必填 | 作用 |
|---|---|---|
| `file` | ✅ | 整条路线的概览单图，决定形状；平时只传它 |
| `details` | ❌ | 沿路线连续截的街道级细节图，拼成大图做完整地理配准，提供真值坐标 |

首次同传时，服务端用 `project_to_geo()` 把多图真值按弧长投影到概览图的形状上，
注册成 `shape_domain="overview"` 的模板；之后形状接近（含反向、不同裁切）的
概览图只传 `file` 就能命中，不必再带细节图。`locate()` 查询概览图时**只比对
overview 域**，旧的 `detail` 域模板保留但不再参与定位，假阳性从根上收敛。

```bash
# 首次 / 换路线：单图 + 可选细节图（本次返回多图配准的真值坐标）
curl -F "file=@whole_route.jpg" -F "details=@shot1.jpg" \
     -F "details=@shot2.jpg" -F "city=上海" \
     http://127.0.0.1:8848/api/recognize

# 之后：只传概览单图，命中已注册的模板
curl -F "file=@whole_route.jpg" -F "city=上海" \
     http://127.0.0.1:8848/api/recognize
```

配对分支返回的叠加底图是拼接画布（`shot_url` 指向 `_stitched.png`，与
`track_polyline_px` 同坐标系），单图放在 `overview_url`；`paired_registration`
给出注册结果与 `pair_match` 诊断。纯单图路径一字未改（`template_capture` 照常
工作、无 `paired_registration`）；没有概览图的纯多图场景仍走
`/api/recognize_multi`。前端对应两个上传控件，并保留「只用细节图」开关。

**召回触发（§22.56）**：原来只有「OCR 判定宽泛概览图」才查模板库——实测
概览图 OCR 宽泛占比 0.373 < 0.5，根本不会去查，注册了也命中不了。现在改为
双通道：宽泛概览图照旧；**库里已有 overview 模板时，任何概览单图都探测一次**，
非宽泛图要求「近复刻」（形状残差 ≤0.045 且 coverage ≥0.90，实测同图重放
residual 0.0021）才采信，否则静默回落原流程。命中时结果卡片显示「历史模板」
行（模板 ID / 残差 / 覆盖 / 是否反向），`locate()` 命中会计入
`hit_count`（`/api/health` 的 `templates.hits` 可观察复用频率）。

⚠️ **双通道是必要条件，不是锦上添花（2026-11-14 实测确认）**：用户上传的
真实概览图 OCR 宽泛占比始终 0.373，旧判据判定永远 false——若只保留宽泛
通道，模板注册成功后也永远不会被召回，飞轮在「注册→召回」之间静默断裂。
「库里有没有资产」本身就是触发信号，不能只依赖输入侧 OCR 启发式。

🔴 **拼接曾会吞掉起终点徽章（已修）**：贴图时同一像素只留**先贴**的那张图，
若含绿色「起」的截图恰好排在重叠区后面，徽章会被同区域另一张「没有徽章」的
截图完整盖掉；画布上再也找不到起点，`extract_track()` 失去拓扑锚，整次识别
直接返回 `ok=false`（真实事故：7 张细节图里 4270 个绿色像素 100% 被覆盖）。
现在 `multishot.stitch()` 会先收集各图的起/终徽章连通域，同深度优先贴含徽章
的图，并在画布裁剪后用各自的变换把徽章（含白字、描边）强制写回；
`stitch.notes` 会给出「已保护 N 枚起终点徽章」。回归见
`tests/test_stitch_badge_protection.py`，详见交接文档 §22.48。

🔴 **失败归因也曾错一整层（已修）**：`track.py` 只在最终画布上找徽章，
一旦拼接弄丢了，它只会报「未检测到起点徽章（绿色「起」）」，听起来像
截图没截到；模板注册失败又一律说「请确认细节图覆盖整条路线且识别自洽」。
现在 `stitch()` 收尾做**产物级守恒校验**：输入各图检出过的起/终徽章，
最终画布必须还在，结果写进 `stitch.badge_conservation`
（`input / canvas / ok / missing`），且只在「输入本来就有」的类别上要求，
不误伤中途没有徽章的正常截图。不守恒时 warnings 首条改为
「拼接阶段丢失了起点徽章（输入第 N 张图有，画布上未检出）」，并注明
后续轨迹/形状告警都是连锁结果；识别失败时不再宣称「本次结果为地理真值」；
模板注册失败按 `paired_registration.reason` 分流给出具体原因。
回归见 `tests/test_badge_conservation.py`，详见交接文档 §22.49。

🔴 **位姿树曾按插入顺序选边，把 7 张图折叠堆叠（已修）**：旧版 BFS 遍历
`link_map.items()`，遇到第一条能连到未定位图的边就固定变换，只保证「跳数最少」，
**完全不看配准质量**。真实事故（2026-11-12 09:04）里 `inliers=549/721/965/725/490`
的强链 0→1→2→3→4→5→6 被 `inliers=25/21/46` 的弱边（0↔5、1↔4、3↔5）
抢先取代，7 张 1260×2720 的图挤进 3077×3818 画布，底部出现明显错位缝，
轨迹只提取到局部 2.8 km；`_verify_canvas()` 因剔除重叠区仍给出 1.0。
现在抽出 `_build_pose_tree()`：**Prim 式最大生成树**，每轮只在「已定位 ↔ 未定位」
的跨接边里选置信度最高的一条（`inliers × ncc`，口径与位姿图平差一致），
等价于让每个节点的位姿来自最强瓶颈路径；权重相同按索引排序保证可复现，
弱边只在没有强边可用时才被用到。`stitch.notes` 会给出「位姿树按配准置信度
选边：N 条，最弱边内点 X」。回归见 `tests/test_pose_tree_selection.py`，
详见交接文档 §22.50。

🟡 徽章守恒只保证**拓扑锚不丢**，位姿树只保证**选边合理**，都不等于拼接
质量合格。事故画布有 17% 空洞、10 对配准被判不可信，轨迹连通域还曾误选底图
色块；修复后同一批图仍有约 18% 空洞与链式累积的纵向漂移（可选
`POSE_GRAPH_ENABLED=1` 做全局平差）。细节图仍要沿路线连续滑动、相邻重叠
约 1/3。另外概览单图在配对模式下只用于注册模板、**不进入识别画布**，
所以它自带的起终点徽章不会参与本次识别。

**配对注册门槛（§22.56 重构后）**：三条折线各 ≥10 点、坐标合法、地理真值
里程在 100m–200km 区间；概览单图形状信息量充足（防「起终点连线」假阳性）；
`match_shape` accepted 且 `coverage ≥0.85`（多图必须覆盖整条路线，否则
`partial_route` 拒收并提示补截）。**画布轨迹扁长、单画布置信度封顶（0.2）、
画布 `input_quality` 不再连坐**——配对真值的可信度来自多图拼接证据
（拼接成功 + 逐像素复核 ≥0.5 + 徽章守恒 + 识别产出几何），自洽性仍是硬门。
参考级结果带 `template_derived` 标记，**永不沉淀**——飞轮里只有配对注册
能新增 overview 模板。

实测（2026-11-13 真实概览图 + 拼接画布复盘）：概览↔画布配对 residual
**0.0116**、coverage 1.0；重构后 conf 0.2 直接过门注册；同图重放 locate
residual **0.0021**、coverage 1.0，近复刻采信成立，反向变体同样命中。

实测闭环（2026-11-14 用户两次真实上传）：① 传「概览 + 7 细节图」，SIFT

`diagnostics.template_match` residual **0.00207**、coverage 1.0 命中，

贴着参考级上限 0.45，`template_capture.written=false
(reason=template_derived_result)` 证明模板派生结果不回写。

# 高德（推荐，与美团底图同源，POI 标注位置最一致）
AMAP_KEY=你的密钥
# 或腾讯 / 百度 / 天地图
TMAP_KEY=
BAIDU_MAP_KEY=
# 天地图 tk（只认这一个变量名）
TIANDITU_API_KEY=

前者只多一份「沿路折线」供人工对照，后者只把链式拼接的累积漂移分摊到
各图，都不改地理配准主结果。低信息量直线输入仍由护栏强制跳过。
详见交接文档 §22.40。

未配置密钥时自动降级为纯本地词典模式，功能可用但只能识别词典覆盖的区域。

`tianditu,amap` 保留高德兜底），无需改代码；`.env` 改完即时生效，不必重启。
③ 道路几何与 ④ 路线校验用的是公共 OSM 服务、无需密钥，可用上面两个
`*_ENABLED=0` 开关整体关闭。

**能力层约定**：后端四类能力（① 地理编码 / ② 路名 / ③ 道路几何 /
④ 路线校验）都通过 `src/app/maps/` 的契约、凭证、注册表与 HTTP 基座装配。
每个 provider 必须声明 `output_crs`，框架统一换算到 GCJ-02；Overpass
镜像表与轮换、Session/UA/限流/重试、路由结果磁盘缓存各只有一份实现。
`/api/health` 新增 `maps.road_geometry` 与 `maps.route_validation`
字段上报装配顺序（只读注册表、不打公共实例），新增服务商不需要改
`server.py`。详见 HANDOVER §22.30–22.31。

**网页底图**：前端底图走独立适配层 `src/web/js/basemap.js`，业务代码不直接
调用 `TMap.*`。已注册 `tmap`（腾讯 GL JS）与 `amap`（高德 JS API 2.0）
两个实现，改 `.env` 的 `BASEMAP_PROVIDER` 即可切换，无需改代码；
`/api/health` 的 `maps.basemap.provider` 会显示当前服务商。
注意高德 JS SDK 用的是**前端 key**（`AMAP_JS_KEY` + `AMAP_JS_SECURITY`），
与 WebService 的 `AMAP_KEY` 是两套凭据；没配时会自动回退腾讯，避免白屏。
详见 HANDOVER §22.32。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 服务状态、可用地理编码能力、词典统计 |
| POST | `/api/recognize` | 上传截图，返回 GeoJSON 轨迹与诊断信息 |
| POST | `/api/recognize_multi` | 多张截图拼接成一张画布后识别 |
| GET | `/api/refine/{shot_id}` | 查询后台路网精修进度与结果 |
| GET | `/api/shots/{name}` | 回传原图，供前端叠加显示 |
| POST | `/api/feedback` | 提交锚点纠正，写入词典 |
| POST | `/api/feedback/reset` | 清空全部人工纠正（body 需 `{"confirm": true}`，保留自动点位） |
| GET | `/api/lexicon` | 查看词典内容与统计 |
| GET | `/api/lexicon/export` | 导出词典 JSON |

`POST /api/recognize` 表单字段：`file`（图片）、`city`（城市提示，可选）、
`output_crs`（`WGS-84` / `GCJ-02`）、`allow_online`（是否允许在线地理编码）、
`refine`、`road_names`。多图接口用 `files` 代替 `file`。

### `refine` 参数与多图精修

| 取值 | 单图 | 多图 |
|---|---|---|
| 不传 / `auto`（默认） | 主请求先出粗结果，后台**补算贴路平移**，前端轮询刷新 | 后台只做**路网校验 + 路名归属**，不平移 |
| `on` | 同步执行完整精修（阻塞请求） | 同步执行完整精修；12 图拼接实测约 264 秒 |
| `off` / 其他 | 不精修 | 不精修 |

后台精修**不重跑 OCR / 轨迹提取 / 在线锚点 / 配准**：主请求把 `reg`、
简化折线、锚点、缩放评估留在 `PipelineResult.refine_context`（只在进程内，
不进接口响应），后台只调 `Pipeline.refine_existing` 补算平移量并重新投影。
结果里 `road_fit.mode == "verify"` 表示「只校验没平移」；
`GET /api/refine/{shot_id}` 在任务运行中额外返回 `elapsed_s`。

精修被护栏否决时（`road_fit.ok == false`），输出位移仍为 0，但会额外给出
`candidate_shift_e_m/n_m`（搜索出的候选平移）、`candidate_median_after_m`
和 `candidate_shift_px`（按配准矩阵逆换算出的截图像素位移）。前端据此在
「原始截图」叠加层用**橙色虚线**画出未采纳的路线，并在状态条与路网卡片
说明拒因，便于人工判断护栏是否误拒。多图默认 `verify` 档不产生候选解，
因此不会画线；换图时图例自动清空。

**候选位置可在地图上切换对照**：精修被否决时，状态条下方会出现
「在地图上查看未采纳的贴路位置」按钮。点击后底图改为显示候选轨迹
（与主轨迹平移同一个墨卡托位移），再点即切回。这只在**显示层**生效：
结果坐标、GeoJSON 下载、里程与置信度始终是初次识别位置。护栏两侧证据
冲突时（贴路大幅改善、但锚点残差同时变坏），由用户自己判断，系统不替他拍板。
被否决的后台精修结果也会写回 `last_result.json`（只保留 `shot_id` 一致性保护），
因此刷新页面后橙线、拒因与切换按钮都还在。

### 截图里只有「起终点连线」时

美团在路线概览 / 低缩放页面会把骑行轨迹渲染成一条带箭头的**笔直连线**，
而不是沿道路曲折的实际轨迹。这类输入无论配准多准、精修是否采纳，输出
都只能是一条横穿街区的直线。流水线用三个同时成立的条件识别它：
折线「直线度」（端点弦长 / 折线总长，`diagnostics.track_straightness`）≥ 0.80、
轨迹框长宽比 ≥ 4、且截图里没有可辨认的街道名锚点。单独看直线度会误判
「沿一条直路骑」的真实轨迹（实测 12 图拼接样本直线度 0.869、长宽比 2.0）。
命中时 `warnings` 会明确说明「只能定位到街区级，无法还原沿路走向」，并建议
重截包含完整轨迹曲线的页面、放大到能看到道路名，或填写「你记得走过的路」。
判据只看形状与锚点类型，与截图分辨率、城市、坐标系无关。

多图默认不平移的原因：拼接画布只有**一个刚体配准**，12 张链式拼接
（depth=10）的累积漂移会被当成「配准误差」，用一个平移量去贴路很容易
把整条轨迹压到平行的主干道上。前端「贴路校正」开关勾选后才会发
`refine=on`，由用户显式承担耗时与风险。

位移搜索对轨迹点等距抽样（`AppConfig.road_fit_eval_budget`，默认 2000）：
大画布 1.1 万个轨迹点 × 4225 个位移候选约 4700 万次 KD 树查询，抽样后
查询量降一个数量级；**搜索空间、护栏、位移限幅依据的轨迹长度都不变**，
设 0 可关闭抽样。

响应中同时提供两份 GeoJSON：

| 字段 | 坐标系 | 用途 |
|---|---|---|
| `geojson` | WGS-84 | GPS 设备、GIS 工具、Strava 等 |
| `geojson_gcj02` | GCJ-02 | 腾讯/高德/百度底图直接绘制 |

两份的 `properties` 里都带 `direction: first_point_is_start`，
明确 **LineString 第一个点是起点**。

## 地图底图合规

底图渲染与在线地理编码**仅使用腾讯地图 / 高德 / 百度 / 天地图**四家持牌服务，
不使用 OpenStreetMap 直连瓦片、Mapbox、Google Maps、Leaflet + OSM 等
境外或未备案数据源。

**密钥不下发到浏览器**：腾讯地图 GL JS 的鉴权请求（`checkKey` 等）由本地服务
代理转发（`src/app/tmap_proxy.py`），key 只存在于服务端。
页面里只有随机生成的代理标记（`_wbt/<随机串>`），拿不到真正的 key。

底图默认用腾讯地图官方公开示例 key（仅用于渲染底图）；用户配置了自己的
`TMAP_KEY` 则优先用用户的。**地理编码仍需用户自己申请密钥**——
示例 key 没有 WebService 配额。

**关于 OSM 的使用边界**：OSM 在本项目中**只提供坐标与几何参考**，
不参与底图渲染，也不作为首选地理编码来源——

- `src/app/roadfit.py`：OSM 路网几何用于「轨迹必须走在真实道路上」的几何判定与精修
- `src/app/coldstart.py`：OSM 名称检索用于词典未覆盖区域的冷启动兜底，
  优先级低于用户确认与四家持牌服务，结果标记为 `osm` 源并由路网精修纠正偏差
- `src/app/seed_lexicon.py`：词典种子同样来自 OSM 名称检索（viewbox 限定）

页面底图始终是腾讯地图；坐标来源优先级见「③ 地理编码」。

**为什么 `app/` 在 `src/` 下面**：`app` 是可导入的 Python 包，放在 `src/` 布局里
能避免「仓库根目录被 `sys.path` 污染」——`tests/`、`tools/` 里的脚本
`import app` 时命中的一定是 `src/app/`，不会误import到别处的同名目录。

> ⚠️ `src/app/config.py` 的 `ROOT` 由**目录结构自动探测**（向上找最近的含
> `data/` 的祖先目录），不是固定层数。因为同一份代码会被打包进技能包，
> vendor 布局是 `<core>/app/` + `<core>/data/`，与仓库布局差两层。

## 精度天花板

截图分辨率决定了定位精度上限。1 像素 ≈ 4.6 米，且 POI 文字标注本身有 35-150 m
的固有偏移，因此**不会**因为数据积累而突破 10-30 米量级。

要再往下走，需要更高分辨率的原图，或直接从 App 获取原始轨迹数据。

## 通用性约定：换一批截图不用改代码

识别链路刻意把「算法」与「数据 / 常数」分开，避免针对某一次上传的截图
调分支、调阈值、写名单：

| 东西 | 放在哪 | 依据 |
|---|---|---|
| 像素阈值 | `src/app/scale.py` | 无量纲系数 × 标尺（画布对角线 / 徽章直径），见交接文档 22.22 |
| 物理阈值 | `src/app/config.py` | 米/像素、米；如 `road_fit_low_zoom_m_per_px` |
| 地理参考数据 | `data/waters.json`、`data/seed_lexicon.json` | 河流岸线/半宽、POI 锚点坐标与 OCR 别名，可整体替换 |
| 统计样本量 | 业务代码里的少量常量 | 与分辨率无关（如 NCC 需要几百个像素才稳定） |
| 位移类阈值 | `src/app/config.py` | 绝对上限 + 被修正对象自身尺度的无量纲比例，二者取小，见交接文档 22.27 |

- 水系数据可用 `RIDE_WATERS_JSON` 指向自己的文件，POI 种子用
  `RIDE_SEED_LEXICON_JSON`；换城市不用改代码。
- 可视化产出用固定文件名，样本之间用输出目录隔离；路网验证图画哪些路
  由识别结果 `road_attribution` 决定，配色按路名摘要稳定生成。
- `tests/test_no_sample_customization.py` 会静态检查核心模块里没有样本
  文件名、样本专属路名或固定经纬度，并验证地理数据可热替换。
- 任何「把结果整体挪动」的优化，位移上限不能只给绝对米数：必须同时受
  被修正对象自身空间尺度的比例约束。否则换一条更短的轨迹，同样的
  绝对上限就足以把它贴到另一条平行道路上（22.27 的真实回归）。

排查文档里出现的「实测某张图误差多少米」只是**验证用例**，
不进入任何识别判据。
