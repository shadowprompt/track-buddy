# 美团骑行截图轨迹识别

从美团骑行 App 的**地图截图**中还原骑行轨迹，输出 GeoJSON。

GPS 坐标不在图片里——截图只是一张渲染好的地图。本项目用图上已知的地理参照物
（POI 标注、地铁站、比例尺）作为锚点，把「像素坐标系」配准到「经纬度坐标系」，
再把提取出的轨迹像素折线反投影为 GPS 点序列。

---

## 📘 交接文档

**接手本项目请先读 [`docs/HANDOVER.md`](docs/HANDOVER.md)** ——
完整的项目设计、模块职责、坐标系约定、算法细节、API 契约、
已知坑与排障手册、决策记录。

一句话概括本项目：**这不是图像识别，是图像配准**。
GPS 坐标不在图片里，要用图上印的 POI 标注当锚点做像素→经纬度映射，
再用真实路网约束校正。

## 路网约束精修（关键一步）

配准的锚点是 **POI 文字标注**，而标注位置由地图排版决定，且 POI 坐标来自
不同数据库：美团底图用高德/腾讯的国内 POI 数据，而词典种子来自
OSM/Nominatim。同一 POI 在两套数据里可差 100-300 米。

实测长宁新泾一例：锚点全部来自 OSM POI 点，配准整体偏了约 326 米，
轨迹落到了**平行的错误道路族**上——用户实骑 新渔路/新渔东路/剑河路/金钟路，
而 OSM 归属显示 天山路/北翟路/淞虹路。两者几何一致、命名不一致，
贴路看起来都"还行"，只有用户知道骑的是哪条路。

修法分两步：

1. **修正地理编码优先级**（`app/geocode.py`）：用户确认 > 在线服务（与美团
   底图同源）> 本地词典。早期实现是「词典优先」，只要词典命中就永不调用
   在线服务，配了 `AMAP_KEY` 也用不上——这是根因。
2. **路网约束精修**（`app/roadfit.py`）：道路几何不存在基准不一致的问题。
   在保持尺度与朝向的前提下平移轨迹，使贴路距离最小，再把平移量并入配准
   矩阵。实测贴路中位距离 61 m → 5 m，路名归属随即输出为用户实骑的那几条。

这一步同时解决了「这条轨迹骑的是哪几条路」——它是轨迹与真实路网的
几何并集，比任何 POI 查询都可靠。

**教训**：单一指标变好 ≠ 位置更准。当时曾用「平移后贴路距离最小」找最优解，
方向是对的；但用「到 OSM 最近顶点的距离」当判据时出现了假阴/假阳——
只测"到最近点"而不测"线路是否沿这个方向延伸"，会把一个恰好存在的顶点
误当成吻合。

## 坐标系转换：一个让整条链路偏 400 米的 bug

`app/geo/coords.py` 里的 GCJ-02 转换曾经有一个**万里挑一的实现错误**：

```python
dlat, dlon = _transform_lat(lon - 105.0, lat - 35.0)   # ← dlon 也取了 lat 的结果
```

`_transform_lat` 返回 `(ret, ret)`，所以 **`dlon` 拿到的是纬度变换的值**——
`_transform_lon` 是死代码，从未被调用。这个错误被"两个值相同"完全掩盖住了，
所有看起来正常的测试都通过。

代价有多大：纬度精确，**经度偏差 375 米**。上海实测 GCJ-02 偏移应为
**东 +438 m、南 −208 m**，错误版本算出的是东 −207 m——**方向都反了**。

更糟的是这个偏差会进入**每一个锚点**，然后被"路网约束精修"当成真实位置误差
去纠正，于是整条轨迹被推到了平行的错误道路族上。

**怎么发现的**：用公开的权威基准点校验——

```
天安门  WGS-84 (116.391349, 39.907375)  →  GCJ-02 (116.397590, 39.908776)
```

修复后误差 **0.0 m**。这条断言现在写进了 `tests/test_e2e.py`，
是最先能抓住此类问题的守门测试。

**教训**：涉及坐标系转换的代码，**必须用外部权威基准点做单元测试**，
不能只验证「往返无损」——往返无损在错误实现下同样成立。

顺带修掉的还有 `roadfit.py` 里的基准混用：轨迹是 GCJ-02 墨卡托，
OSM 路网是 WGS-84 墨卡托，两者直接比较会引入约 470 米的伪偏移。

## 支持的路线形状：不要再用「横向延展」当启发式

早期连通域筛选要求轨迹的包围盒 **aspect > 1.6**（横向延展）。这在第一张
样本（东西向长距离）上碰巧成立，但对**对角线或南北向路线会整条漏掉**——
第二张样本 aspect ≈ 1.03，管线直接返回「未找到轨迹连通域」。

现在改成拓扑驱动：

1. 用包围盒粗筛候选（同时靠近两个徽章、面积够大）
2. 对最接近的若干候选做**像素级精确测距**：连通域到「起」「终」两个徽章的
   最近像素距离
3. 取总距离最小者；超过 260 px 则判定「不是轨迹」

退化情况（未检出徽章）用「填充率」筛掉文字团块。

## 输出坐标的反投影必须与提取轨迹重合

交付可视化时踩过两次同样的坑：**把已经是 GCJ-02 的坐标又做了一次
`wgs84_to_gcj02`**，凭空多出约 500 米（100+ 像素）的偏移，画出来轨迹明显
偏离原图，还以为是算法错了。

现在 `tests/test_e2e.py` 里有一条断言守住它：**输出坐标反投影回像素后，
必须与提取的轨迹像素重合（阈值 3 px，实测中位 0.24 px）**。
同理，校验绝对位置时也绝不能重复换算基准。

## 换一张截图就崩：三个叠加的坑

换成新区域的截图后，页面直接报
`识别失败：Cannot read properties of undefined (reading 'toFixed')`。
这句话本身没有信息量——它是一层**假象**，真正的失败在下面三层。

### ① 前端：失败响应没有字段，前端又直接 `.toFixed()`

后端在配准失败时只返回 `diagnostics = {"track_points": N}`，
前端却直接写 `dg.rotation_deg.toFixed(2)` → `undefined.toFixed` 抛 TypeError
→ 被 `catch` 捕获 → 显示成「识别失败」。

**后果比报错本身严重**：真正的失败原因（`warnings` 里写着
「所有锚点均未匹配到坐标」）被这个异常整个吞掉，用户无从得知发生了什么。

修法有两条，缺一不可：

- 后端所有失败路径都返回**结构一致**的 diagnostics（`DIAG_KEYS` + `_base_diagnostics`）
- 前端所有数值字段走安全格式化（`num()` / `int()` / `text()`），缺失显示「—」

顺带修掉的同类崩溃点：`drawMap` 在空几何上取 `features[0]`、
`drawPreview` 用 `image_size=[0,0]` 做除法、失败时 `warnings` 未做 HTML 转义。

### ② 后端：新区域没有坐标来源

词典只有已核验的 38 个上海地名，新截图里的「安龙小区」等全都不在其中，
又没配地图密钥 → 0 个锚点 → 配准失败。

补上 **OSM 冷启动**（见「③ 地理编码」）。修复后同一张截图：

```
置信度 0.791   轨迹点 43   里程 447.9 m
贴路中位距离 2.8 m → 2.3 m
经过道路：新渔东路 → 安龙路        ← 与截图上印的路名一致
```

### ③ 算法：两个与「尺度」有关的隐藏 bug

新截图是**高倍截图**（`scale = 0.22 m/px`，而旧样本是 4.5 m/px），
暴露了两处只在小尺度下才发作的问题：

**采样步长与简化容差没有像素上限。** 10 米的步长在 `scale=0.26` 时
换算成 38 像素，一个弯道就被跳过；2 米的容差变成 7.7 像素，把弯道全削平了
——1990 像素的轨迹最后只剩 **6 个点**。现在两者都加了像素上限
（步长 ≤ 4 px，容差 ≤ 1 px）。

**经典 Douglas-Peucker 在近直线上失效。** 它用「到端点连线的垂距」作判据，
而一条南北向长直线上任何微小横向抖动都会被这段长直线放大成很大的垂距。
实测轨迹总长 2043 像素、端到端直线 1954 像素（仅 4.5% 蛇形），
简化后只剩 32 个点，弯道全部消失。

改用**弧长偏差**作主判据（折线比弦长多走了多少路，与「直线很长」无关），
垂距只用来定位分裂点。实测弧长保留 98.5%，最大偏离原轨迹 0.54 像素。

### 顺带修掉的坐标系 bug

`_road_refine` 把 `reg.pixel_to_lonlat()` 的 **GCJ-02** bbox 直接喂给
OSM API（它期望 **WGS-84**），查询中心因此偏移约 450 米（东）/200 米（南），
拉回来的是**别的街区**的路网。现在先转 WGS-84 再查询。

> **教训**：这三个 bug 有同一个共同特征——**只在旧样本上看不出来**。
> 旧样本尺度大（4.5 m/px）、区域在词典内、且必然成功。
> 换一张截图就同时踩中三个。**必须用不同区域、不同缩放级别的多张图来验证。**

## 只在浏览器里才会犯的两个 bug

这两个问题的服务端日志**全是 200**——识别本身是成功的，错误发生在
识别完成之后的渲染阶段。所以跑后端测试永远发现不了。

### 连续识别报「Unhandled error. (undefined)」

**真正的根因是腾讯地图鉴权失败，不是「连续识别」本身。**

`Unhandled error. (undefined)` 这句话来自 Node.js 的 `EventEmitter` 标准实现：

```js
var s = new Error("Unhandled error." + (a ? " (" + a.message + ")" : ""));
```

即某个组件触发了 `'error'` 事件但**没有监听器**，且第一个参数不是 `Error` 实例。
腾讯地图 GL JS 鉴权失败时走的正是这条路。

**鉴权为什么会失败**：`web/index.html` 里的

```js
serviceHost: 'http://127.0.0.1:__WB_HTTP_PORT__/_TMapService/_wbt/__WB_TMAP_SECRET__',
```

这两个占位符**从来没有被任何代码替换过**——README 承诺的「本地代理」
根本不存在。SDK 于是去请求一个非法地址（`__WB_HTTP_PORT__` 不是合法端口），
鉴权必然失败 → SDK 内部 `AUTH_ERROR.netError` → 触发 `'error'` 事件 →
抛出没有上下文的 `Unhandled error. (undefined)`。

而我们的 `catch` 把它包装成了「识别失败」——**把一个底图问题说成了识别问题**。

**修法**：

1. 实现 `app/tmap_proxy.py`：真实转发 `checkKey` / `oversea` / `pingd` 到腾讯地图上游，
   在服务端注入 key，浏览器永远拿不到 key
2. 首页改为动态渲染（`app/server.py` 的 `index()`），把端口与随机代理标记填进页面
3. 底图 key 用腾讯地图官方公开示例 key（`config.TMAP_PUBLIC_KEY`），
   用户配了自己的 `TMAP_KEY` 则优先用用户的
4. **把「识别」与「渲染」彻底分开**：接口失败才显示「识别失败」；
   渲染失败只提示「识别已完成，但地图渲染出错，GeoJSON 可正常下载」
5. 附加防护：容器尺寸为 0 时不操作地图、`fitBounds` 加尺寸检查与 try-catch、
   识别完成后调用 `ensureMapReady()` 确保地图就绪

> **教训一**：README 里写了「腾讯地图 GL JS 走本地代理」——但代码里没有。
> **文档描述了一个不存在的实现，比没有文档更糟**，因为它让人以为底图是正常的。
>
> **教训二**：第三方 SDK 的错误信息可能完全没有上下文。
> 遇到 `Unhandled error. (undefined)` 这类消息，第一反应应该是
> **「这到底是谁抛的？」**——用 grep 在项目里搜这个字符串，零命中就说明不是我们的代码。
>
> **教训三**：真实浏览器测试是唯一可靠的手段。
> 前两轮修复（容器尺寸检查、隐藏时跳过）方向都对但都不是根因，
> 只有 Playwright 抓到真实的 `pageerror` 才定位到真相。
> 见 `tools/verify_browser.py`。

### 识别成功了，但地图上的轨迹还是上一张的

这个坑比前面两个更隐蔽：**左栏数据全部是新图的**（置信度、轨迹点、里程、
路名都对），**只有地图是旧的**——轨迹线还在上一张截图的位置，
视野也停在上一片区域。

根因在腾讯地图 GL JS 的 `removeLayer`：

```js
// SDK 源码（压缩后）
i.removeLayer = function (t) {
  var e = this._layers[t];            // ← t 是图层 id 字符串
  e ? (e._setEventedParent(null), delete this._layers[t])
    : this._fire("error", { error: new Error("The layer '" + t + "' does not exist in map") });
}
```

而我们的代码传的是**图层对象**：

```js
map.removeLayer(polyline);   // ✗ polyline 是 MultiPolyline 实例
map.removeLayer(polyline.id) // ✓ 传 id
```

传对象 → 查不到 → 抛 `The layer '[object Object]' does not exist in map`
→ **异常中断 `drawMapInner`** → 后面 `lastPath = path` 没执行、
新轨迹也没画 → `fitBounds` 仍按旧路径定位视野。

外层 `drawMap` 的 catch 只 `console.error`，于是完全静默：
左栏照常更新（那部分在 `drawMap` 之前就渲染完了），地图却停在上一张。

实测证据（浏览器 console）：

```
Error: The layer '[object Object]' does not exist in map
    at i.removeLayer (gljs.js:69:395974)
    at drawMapInner (http://127.0.0.1:8848/:498:17)
```

修法：`removeLayer(layer.id)`。同时把图层清理包进 try/catch，
避免 SDK 行为变化时再次静默中断整段绘制。

> **教训**：这次的定位路径值得记住——
> ① 浏览器 console 里的报错指向 SDK 内部，就去翻 SDK 源码；
> ② 压缩代码里 `this._layers[t]` 这种形式直接说明了参数的语义；
> ③ 用一个只接受 id 的桩复现真实行为，测试就能抓住它
> （`tests/test_frontend.py` 的场景 6 就是这么写的）。

### 原图面板与地图面板同时显示

### 右侧的两个可视化面板：应该同时可见，而不是互斥切换

用户的预期一直是「**右侧上方是识别到图片，右侧下方是原始图**」——
两个都要看得到：地图用来确认位置对不对，原图用来确认轨迹有没有抠错。

历史上这里做成了「地图 / 原图叠加」两个**标签页互斥切换**。
识别完成后停在「地图」页，原图整个消失，用户反馈
「右侧下方原始的怎么都不显示了」——看起来像功能坏了。

改成上下堆叠、两个面板同时可见：

```html
<div class="vis-block">
  <div class="vis-title"><b>识别结果</b><span class="hint">腾讯底图 · GCJ-02</span></div>
  <div id="map"></div>
</div>
<div class="vis-block">
  <div class="vis-title"><b>原始截图</b><span class="hint">绿色为识别出的轨迹，黄色为锚点</span></div>
  <div id="preview"><img id="prevImg"><canvas id="prevCanvas"></canvas></div>
</div>
```

`switchTab()` 随之改为 `ensureMapReady()`：只负责「确保地图已创建、
尺寸正确、视野对准轨迹」，不再管显隐。

> **教训**：互斥切换看起来更"干净"，但它与用户的实际工作流冲突——
> 校验识别结果时，地图和原图是要**对照着看**的。
> 把两个东西藏进标签页，用户就得反复来回切。
> 这类交互设计要问的是「用户想同时看到什么」，
> 而不是「怎么排版看起来整齐」。

## 三个最容易踩的坑

### ① 道路名不能作锚点（最严重）

地图把路名**沿道路/河流走向排布**，文字中心不对应任何固定地理位置。
实测同一张图上：

| 锚点类型 | 真值反投影偏移中位 | 最大 |
|---|---|---|
| POI 类（公园/宾馆/广场/车站） | **32 px**（≈170 m） | 192 px |
| 道路类（大渡河路/祁连山南路/桃浦河…） | **458 px**（≈2.5 km） | 1637 px |

早期版本把道路名也当锚点，结果**整体平移 3 公里**。而 RMSE 完全看不出来
（RMSE 只反映锚点之间的自洽性，不反映绝对位置）。

**对策**：
- 竖排文字几乎必然是道路名，直接排除
- 词典只收录 POI 类条目
- 加**绝对位置自校验**：把内点锚点的真值反投影回像素，若不落在它自己
  文字附近就告警并降低置信度。这个检查能自动抓住「坐标对错同名地点」

### ② GeoJSON 的坐标顺序与方向

- **坐标系**：腾讯/高德底图是 GCJ-02，比 WGS-84 多约 350 米偏移。
  把 WGS-84 坐标直接画在腾讯底图上会整体偏 350 米。
  接口同时返回 `geojson`（WGS-84）和 `geojson_gcj02` 两份，前端用后者。
- **方向**：GeoJSON 的 LineString 坐标顺序即绘制顺序，本项目保证
  **第一个点是起点、最后一点是终点**，并在 `properties` 里显式声明
  `direction: first_point_is_start`。很多第三方工具默认「首点=起点」
  来标注起终点，顺序反了地图上就会画反。

### ③ 校验要选独立参照

「反投影回截图后与原轨迹吻合」只证明**自洽**，不证明**位置正确**。
绝对精度必须用第三方数据（真实路网）验证：
轨迹贴在路上只能说明它走在某条路上，不能说明是哪条。

## 五个阶段

```
截图
 ├─ ① 轨迹提取   色彩分割 → 形态学 → 连通域 → 骨架化 → 图路径追踪
 ├─ ② OCR        RapidOCR（支持竖排/旋转文字）→ 锚点候选
 ├─ ③ 地理编码   四级：用户确认 > 在线服务（高德/腾讯/百度/天地图）
 │                > 本地词典 > OSM 冷启动
 ├─ ④ 配准       RANSAC + north_up 模型 → 像素→墨卡托变换矩阵
 │                + 绝对位置自校验 + 路网约束精修
 └─ ⑤ 反投影     折线 → 经纬度 → GeoJSON（WGS-84 + GCJ-02 两份）
```

### ① 轨迹提取

轨迹线是「深色描边 + 浅灰填充」的双层结构，不能用暗阈值直接提取。用
**低饱和 + 中等亮度** 的掩膜：地图底色是蓝灰（饱和度高）被排除；文字笔画虽暗
但只有 2-3 px 宽，而轨迹线宽 8-10 px，靠开运算分离。

起终点用 HSV 找大色块（绿色「起」、红色「终」）。面积阈值是关键：徽章约
4000+ 像素，而虚线碎片只有 100-300，相差一个数量级。红色虚线（规划路线）
饱和度高，被饱和度条件天然排除。

骨架化后**在 8 邻接图上用 Dijkstra 搜索起→终路径**，而不是按投影排序。
原因见下方「踩过的坑」。

### ② OCR 与锚点分级

| 类型 | 例子 | 锚点价值 |
|---|---|---|
| icon | 带图标的 POI | 最优，图标锚点即真实位置，误差 2-3 px |
| poi | 上海动物园、西郊宾馆 | 好，文字中心偏移 7-28 px（35-150 m） |
| road | 曹安公路、大渡河路 | **不作为锚点**，只做区域校验 |

道路名的反投影偏移比 POI 大一个数量级（详见「三个最容易踩的坑」①）。

### ③ 地理编码

四级优先级，越靠前越可信：

1. **用户确认** — 网页上点过地图纠正的地名，最高优先级
2. **在线服务** — 按已配置的密钥自动选择高德 / 腾讯 / 百度 / 天地图。
   这些与美团底图同源，POI 坐标没有基准偏差
3. **本地词典** `data/lexicon.json` — 离线可用，精度受限于种子来源
4. **OSM 冷启动** `app/coldstart.py` — 前三级都没命中时的最后一道网

返回多个候选时全部交给 RANSAC，由几何一致性挑选，天然处理同名地点歧义。

**为什么需要第 4 级（冷启动）**

第 3 级只覆盖已核验过的地名。换一个区域就完全无法识别：实测长宁剑河路
一带，OCR 明明读出了「安龙小区」「新安小区」「珍宝公寓」「长宁实验小学」
这些真实地名，却因为「词典里没有、也没配密钥」而拿到 0 个坐标，配准直接失败。

冷启动按城市限定范围去 OSM 检索这些地名。这与本项目既有做法一致——
`app/seed_lexicon.py` 的初始词典种子本来就是「viewbox 限定的地理编码查询」
得到的。检索结果标记为 `osm` 源（权重低于用户确认与在线服务），
并写回词典形成数据飞轮；它的 100-300 米基准偏差由第 ④.5 步的路网精修纠正。

**冷启动的三阶段策略**（`app/coldstart.py`）

早期版本「要求完全同名 + 城市级 viewbox」，在浦东实测**6 个 POI 全部 0 命中**。
三个原因分别对应三个阶段：

*阶段一 · 多查询变体* — Nominatim 的索引对前缀敏感，同一个 POI 换个写法
结果就不同：

| 查询 | 结果数 |
|---|---|
| `进才实验中学 上海` | 0 |
| `上海市进才实验中学` | 1 ✓ |

所以每个地名用多个变体检索：`{名} {市}`、`{市}{名}`、`{短名}{名}`、`{名}`。

*阶段二 · 名称相似度* — OCR 会截断地名，不能要求完全同名：

| OCR | OSM 实际名称 | 相似度 |
|---|---|---|
| 进才实验中学 | 上海市进才实验中学 | 0.92 ✓ |
| 水清木华 | 水清木华公寓 | 0.92 ✓ |
| 乡土田园区 | 何文田上海水配水庫 | 0.08 ✗ |

低于 0.55 直接丢弃。用 Jaccard 字符相似度 + 子串加权。

*阶段三 · 多锚点互证* — 单个地名无法自证位置：「花园2期」能匹配到
朗香/星宇/尼德兰/三湘盛世四个不同小区的「2期」，取哪个都可能错。

但**多个独立检索的地名若彼此落在 800 米内**，那这片区域就是真的。
实测浦东一例：华丽家族花园、天安花园、当代清水园、水清木华公寓
四个地名各自独立检索，命中点互相都在 300-500 米内，由此锁定区域中心
`(121.5537, 31.2282)`，再用它过滤掉其余候选——包括那个在安徽的
「水清木华」（同名异地，距离 164 公里）。

这一步**必须批量做**。单锚点无法自证位置，所以 pipeline 里冷启动是
一次性把所有未命中的地名交给 `lookup_many()`，而不是逐个 `geocode()`。

**OSM 检索限速**：Nominatim 使用政策要求最多 1 次/秒，因此冷启动逐个查询，
且查到足够候选就停。结果带磁盘缓存（`data/cache/coldstart.json`），
同一区域再次识别几乎不花时间。

> **一个教训**：viewbox 只是 Nominatim 的**排序提示**，不是强制过滤。
> 对「上海市」这种大范围 bbox 几乎不起作用——同名异地地点照样返回。
> 真正起过滤作用的是自己实现的距离约束与互证。

### ④ 配准

墨卡托投影是保角投影，图像 y 轴向下、墨卡托 y 轴向上，故像素→墨卡托的正北
模型是 `M = [[s, 0], [0, -s]]`，只有 2 个自由度，对锚点噪声极不敏感。

按自由度从低到高依次尝试，优先选精度高的：

1. `north_up` — 正北朝上，2 自由度。默认地图状态，精度最高
2. `similarity` — 允许旋转，4 自由度。适配用户旋转过截图
3. `affine` — 一般仿射，6 自由度。兜底

### ⑤ 坐标系

内部统一 GCJ-02（与截图底图一致），输出可选 WGS-84 或 GCJ-02。
两者在中国境内差约 300-400 m，混用会导致轨迹整体错位数百米。

---

## 坐标系要点

```python
from app.geo.coords import wgs84_to_gcj02, gcj02_to_wgs84

gcj = wgs84_to_gcj02(lon, lat)   # WGS-84 → GCJ-02
wgs = gcj02_to_wgs84(lon, lat)   # GCJ-02 → WGS-84（不动点迭代，精确可逆）
```

`gcj02_to_wgs84` 用不动点迭代求解（GCJ 偏移量依赖原始 WGS 坐标，是隐式方程）。
一步近似会让 GCJ→WGS→GCJ 往返平移 347 m。

另注意：墨卡托尺度 ≠ 地面尺度。地面距离 = 墨卡托距离 × cos(纬度)，
上海一带差 15%。里程用 haversine 计算，不要用「像素长 × 比例尺」估算。

## 「越用越准」的数据飞轮

```
用户上传截图 → 识别 → 地图叠加展示 → 用户确认/纠正锚点
      ↑                                        ↓
      └────── 本地词典（地名词 → 精确坐标）←──┘
```

每次纠正都会强化 `data/lexicon.json` 中对应地名的坐标权重。这份词典是
**唯一会随使用量无限增长的资产**——算法侧的边际收益递减很快，数据侧几乎不衰减。

三个资产的区别：

- **地名词典**：`(城市, 地名) → [经纬度候选 + 权重]`。唯一无限增长，是护城河
- **视觉锚点模板**：图标+文字+像素偏移。有天花板（该城市标注种类有限）
- **评估样本**：`(截图, 真值)` 二元组。价值在于回归测试，不用于训练

冷启动城市没有词典时，靠在线地理编码兜底，但通用 API 对冷门地名覆盖很差。
这时置信度会降低，前端应主动请用户配合，而不是假装很准。

## 地图底图合规

底图渲染与在线地理编码**仅使用腾讯地图 / 高德 / 百度 / 天地图**四家持牌服务，
不使用 OpenStreetMap 直连瓦片、Mapbox、Google Maps、Leaflet + OSM 等
境外或未备案数据源。

**密钥不下发到浏览器**：腾讯地图 GL JS 的鉴权请求（`checkKey` 等）由本地服务
代理转发（`app/tmap_proxy.py`），key 只存在于服务端。
页面里只有随机生成的代理标记（`_wbt/<随机串>`），拿不到真正的 key。

底图默认用腾讯地图官方公开示例 key（仅用于渲染底图）；用户配置了自己的
`TMAP_KEY` 则优先用用户的。**地理编码仍需用户自己申请密钥**——
示例 key 没有 WebService 配额。

**关于 OSM 的使用边界**：OSM 在本项目中**只提供坐标与几何参考**，
不参与底图渲染，也不作为首选地理编码来源——

- `app/roadfit.py`：OSM 路网几何用于「轨迹必须走在真实道路上」的几何判定与精修
- `app/coldstart.py`：OSM 名称检索用于词典未覆盖区域的冷启动兜底，
  优先级低于用户确认与四家持牌服务，结果标记为 `osm` 源并由路网精修纠正偏差
- `app/seed_lexicon.py`：词典种子同样来自 OSM 名称检索（viewbox 限定）

页面底图始终是腾讯地图；坐标来源优先级见「③ 地理编码」。

## 精度天花板

截图分辨率决定了定位精度上限。1 像素 ≈ 4.6 米，且 POI 文字标注本身有 35-150 m
的固有偏移，因此**不会**因为数据积累而突破 10-30 米量级。

要再往下走，需要更高分辨率的原图，或直接从 App 获取原始轨迹数据。
