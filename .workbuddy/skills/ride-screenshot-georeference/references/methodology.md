# 方法论与判据设计（骑行截图 → 经纬度轨迹）

本文记录**不易从代码直接读出**的经验：判据怎么设计、哪些指标会骗人、
踩过哪些坑及其定位方法。深入排查时才需要读。

---

## 1. 为什么这是图像配准问题

GPS 坐标**不存在于图片里**。截图是底图渲染后的位图，理论上无法直接读出坐标。
唯一可行的路径是：

```
像素坐标 ──(锚点: 图上 POI 标注 + 其真实经纬度)──> 经纬度
```

所以整条链路的精度由三件事决定：
1. 轨迹线在像素空间的提取精度（可以做到极高，接近像素级）
2. 像素→地理的映射精度（**主要误差来源**）
3. 基准转换的正确性（错一次就整体偏 500 m）

第 3 项最隐蔽——它不影响任何内部自洽指标。

---

## 2. 五阶段管线

```
截图
 ├─ ① 轨迹提取   色彩分割 → 形态学 → 连通域(拓扑筛选) → 骨架化 → 图路径追踪
 ├─ ② OCR        RapidOCR(PP-OCRv3，支持竖排/旋转) → 锚点候选 → 分级
 ├─ ③ 地理编码   本地词典优先 → 在线服务(与底图同源) → 用户确认
 ├─ ④ 配准       RANSAC + north_up/similarity/affine → 像素→墨卡托矩阵
 ├─ 4.5 路网精修 保持尺度朝向只平移，最小化「轨迹到真实路网距离」
 └─ ⑤ 反投影     折线 → 经纬度 → GeoJSON（同时输出 GCJ-02 与 WGS-84）
```

---

## 3. 坐标系：最容易致命的一环

### 3.1 两种基准

- 中国境内底图（腾讯/高德/美团）用 **GCJ-02**（火星坐标）
- **OSM / GPS 设备 / Strava** 用 **WGS-84**
- 两者在上海相差约 **东 +438 m、南 −208 m**（约 500 m）

### 3.2 权威基准点（务必写进单元测试）

```
天安门  WGS-84 (116.391349, 39.907375)  →  GCJ-02 (116.397590, 39.908776)
```

修复后的实现对这个点的误差是 **0.0 m**。任何坐标系改动后第一件事就是验证它。

### 3.3 实现 bug 的样子（真实发生过）

```python
dlat, dlon = _transform_lat(lon - 105.0, lat - 35.0)   # ← dlon 也取了 lat 的结果
```

`_transform_lat` 返回 `(ret, ret)`，所以 **`dlon` 拿到的是纬度变换的值**，
`_transform_lon` 是死代码。因为两个值恰好相同，这个错误被完美掩盖，
所有「往返无损」测试都通过——而往返无损在错误实现下同样成立。

后果：经度偏 375 m，进入每个锚点，再被路网精修当成「真实位置误差」纠正，
整条轨迹被推到**平行的错误道路族**上。

**教训：坐标系代码必须用外部权威基准点做单元测试，「往返无损」抓不到这类错误。**

### 3.4 重复换算的坑（踩过两次）

`geojson_gcj02` 里的坐标**已经是 GCJ-02**。画叠加图时若再套一次
`wgs84_to_gcj02`，会凭空多出约 500 米（100+ 像素）偏移。

两次都表现为「识别轨迹明显偏离原图」，两次都一度以为是算法问题，
最后靠流水线内部插桩（像素→经纬度→像素往返 0.000000 px）定位到是脚本 bug。

**铁律：画叠加图只能用配准矩阵的逆，绝不重复换算基准。**

## 4. 锚点分级：道路名不能当锚点

实测（长宁新泾一带）文字中心到真实点位的偏移：

| 锚点类型 | 例子 | 偏移中位 | 最大 |
|---|---|---|---|
| POI 类 | 上海动物园、西郊宾馆 | **32 px（170 m）** | 192 px |
| 道路类 | 曹安公路、大渡河路、水城路 | **458 px（2450 m）** | 1637 px |

原因：地图把**路名沿道路走向排布**，文字中心不对应任何固定地理位置。
用它们做锚点会直接毁掉配准。

**路名文字仍有价值**，但只能用于：
- 「区域一致性校验」（判断候选是否落在合理街区）
- 路名归属（`app/roadname.py`，用走向匹配筛掉方向不符的标注）

## 5. 配准模型优先级（自由度从低到高）

| 模型 | 自由度 | 说明 |
|---|---|---|
| `north_up` | 2 | 正北朝上，`M = [[s,0],[0,-s]]`。默认地图状态，**精度最高**（对锚点噪声最不敏感） |
| `similarity` | 4 | 允许旋转，适配用户旋转过截图 |
| `affine` | 6 | 兜底。锚点噪声大时它会给出漂亮但错误的高分拟合 |

RANSAC 退化检查：2 点时**不能**要求 `matrix_rank >= 2`（2 点秩恒为 1）。

## 6. 路网约束精修（`app/roadfit.py`）

**动机**：锚点来自 POI 文字标注，标注位置由地图排版决定；POI 坐标来自不同
数据库（美团底图用国内数据，本地词典种子来自 OSM）。同一 POI 在两套数据里可差
100–300 m，于是轨迹落到**平行的错误道路族**上——几何一致、命名不一致，
贴路看着都「还行」，只有用户知道骑的是哪条路。

**做法**：保持尺度与朝向，**只平移**，最小化「轨迹到真实路网的距离」，
再把平移量并入配准矩阵。实测贴路中位 61 m → 5 m。

**风险**：那一带平行道路密集（相距 100–300 m），「到最近道路距离最小」可能
落到旁边那条路上。必须配合正交判据（见下）。

**同时也是「骑的是哪几条路」的答案来源**：轨迹与真实路网的几何并集，
比任何 POI 查询都可靠。

## 7. 判据设计：五种独立证据

| 判据 | 做法 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **像素级**：轨迹点落在 App 渲染路网上 | 提取渲染路网掩膜，测轨迹像素到最近路网像素距离 | 轨迹**像素提取**精度 | 任何地理假设 |
| **几何级**：OSM 路网投影后落在渲染路网上 | 同上，反向做 | 「像素→地理」映射与底图的一致性 | 哪条平行路是对的 |
| **语义级**：App 自己的路名标签 ↔ OSM 同名道路中心线距离 | 路名印在路面上，距离应很小 | 帧的正确性，**抗平行路欺骗** | 命名差异 |
| **一致性级**：输出坐标反投影回像素须与提取轨迹重合 | 正反变换往返 | 坐标链路内部自洽 | 绝对位置 |
| **交叉级**：不同缩放/不同锚点的两张截图收敛到同一物理点 | 比较两次识别的同一 POI | 尺度与平移都正确 | — |

### 7.1 「到最近点的距离」不是好判据（踩过）

曾用「13号线 标签到 OSM 最近顶点的距离 = 5.6 m」判定位置正确，
并据此否定了用户提供的路名清单。

**错误在于**：只测「到最近点」，不测「线路是否沿这个方向延伸」。
OSM 在那里恰好有个顶点，就被误当成吻合。把整条线投影回图上后，
明显错位。

**几何判据必须用整条形状的吻合。**

### 7.2 「平移最优化」会被平行路骗（踩过）

用「把轨迹整体平移，看平移到哪最贴合真实路网」来反推位置，
最优解是南移 325 m，中位贴路距离从 32.8 m 降到 4.7 m——看起来赢麻了，
而且恰好落在用户报出的路名上。

但另一个判据（路名标签 ↔ 同名道路）否定了它。
原因：那一带新渔东路/天山路/北翟路/金钟路全是东西向平行路，
往南挪 325 米恰好能落在一对更规整的路上。

**单一指标变好 ≠ 位置更准，必须有独立正交证据。**

### 7.3 「渲染路网」作为地面真相

美团底图上道路比背景更蓝：`b - r ≥ 28`（背景 `b - r ≈ 18`）。
据此提取掩膜（再排除地铁线/水系/文字/绿地），即可得到与地理假设无关的
像素级地面真相。

实测命中率：

| 假设 | OSM 路网落在渲染道路上 | 轨迹点落在渲染道路上 |
|---|---|---|
| 仅锚点配准 | 78.8%（中位 4.5 px） | 95.8% |
| 路网精修后 | **85.6%（中位 3.1 px）** | 95.8% |
| 对渲染路网搜索的绝对最优 | 87.0%（中位 2.9 px） | — |

注意「轨迹点落在渲染道路上」这一行**与假设无关**——它衡量的是像素提取精度。

## 8. 轨迹提取

- **掩膜**：`V < 200 且 S < 90`（骑行轨迹是灰白描边，饱和度低）
- **连通域筛选必须用拓扑**：包围盒粗筛（同时靠近两个徽章）+ **像素级精确测距**
  （连通域到「起」「终」的最近像素距离）。**不要用「横向延展 aspect > 1.6」**
  ——那只是对东西向长路线碰巧成立，对角线/南北向路线会整条漏掉
- **骨架化后必须走图路径**（8 邻接图 + Dijkstra），不能按投影排序：
  水平轨迹的垂直段会被交错成锯齿，里程虚增 5 倍
- **重采样要沿折线段插值**：`np.interp` 对 x/y 分别插值会在折角处切角，
  点偏离 60 米
- 简化容差用**米**为单位（2 m），不要用像素（1 px 会把弯道拉直，轨迹削掉 19% 长度）
- 墨卡托尺度 ≠ 地面尺度：地面距离 = 墨卡托距离 × cos(纬度)，31°N 处差 15%

---

## 9. 路名归属的局限

- 归属来源是**几何最近**（OSM 路网），不是官方命名
- 美团与 OSM 的路名常不一致（上海道路改过名，OSM 保留旧名）
- OSM 覆盖稀疏：实测长宁新泾一带「枣阳路」「泉口路」「真北路」各只有 1 个节点

更好的来源是**高德路径规划 API**（与美团底图同源，返回国内官方路名），
需配置 `AMAP_KEY`。

**词典优先级曾写反**：早期是「词典命中就直接返回，永不调用在线服务」，
配了 `AMAP_KEY` 也用不上。已改为 **用户确认 > 在线（与底图同源）> 本地词典**。

## 11. 踩坑清单（按危害排序）

1. **GCJ-02 转换的经度用了错的函数** → 整体偏 375 m，轨迹落到平行错误道路族
2. **反投影时重复换算基准** → 叠加图偏 500 m，误判为算法问题
3. **道路名当锚点** → 配准彻底失准（偏移中位 2.5 km）
4. **地理编码优先级写反** → 配了密钥也用不上
5. **用「到最近点距离」当几何判据** → 假阳性，否定了正确结论
6. **平移最优化被平行路骗** → 需正交证据
7. **连通域用「横向延展」筛选** → 对角线/南北向路线整条漏掉
8. **骨架按投影排序** → 里程虚增 5 倍
9. **重采样对 x/y 分别插值** → 折角切角，偏 60 m
10. **墨卡托尺度当地面尺度** → 里程差 15%
11. **路网缓存不按 bbox 校验** → 用了偏移 4.4 km 的旧缓存，每次都错
12. **`track.bbox` 语义是 (x, y, w, h)** 不是 (x0,y0,x1,y1) → 路网查询范围偏 4 km
13. **验证图的配色与被验证对象撞色** → 轨迹与道路都用黄色，用户无法分辨
