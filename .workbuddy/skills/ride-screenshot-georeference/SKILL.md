# 骑行截图轨迹识别与地理配准

## 概述

把一张骑行 App 的地图截图还原成带经纬度的轨迹文件。

这不是「图像识别」问题，而是**图像配准**问题：GPS 坐标不在图片里，需要用图上
的 POI 标注当锚点，把像素坐标映射到经纬度，再用真实路网约束校正。

**技能自带识别内核**（`assets/ride_core/`，含 app 包与本地词典），
复制到任何装了 Python 依赖的机器即可独立运行——不依赖 `D:\Dev\meituan-ride`
存在。本技能封装调用方式、结果解读方法与**踩过的坑**。

开发仓库在 `D:\Dev\meituan-ride`（代码唯一真源）；改完用
`python tools/sync_skill.py <技能目录>` 把内核同步进各份技能安装。

## 何时使用

- 用户发来骑行/运动记录截图，要求导出轨迹、GeoJSON、GPX
- 用户问「我骑的是哪几条路」「这条路线在什么位置」
- 用户反馈「识别出的轨迹不在实际道路上」「坐标偏了」「终点跑到别的街区了」
- 需要把轨迹画到腾讯/高德底图上核对

## 快速开始

```bash
python scripts/recognize.py <图片路径> --city 上海 --out <输出目录>
```

脚本会定位内核目录并调用 `python -m app.cli`。stdout 输出一段 JSON 摘要，
包含置信度、里程、起终点经纬度、路名序列、诊断指标与产出文件路径。

内核定位顺序：

1. 环境变量 `MEITUAN_RIDE_HOME`（开发时指向代码仓库）
2. **技能自带的 `assets/ride_core/`** —— 便携路径，默认走这条
3. `D:\Dev\meituan-ride`

也可以直接调用 CLI（等价）：

```bash
python -m app.cli <图片> --city 上海 --out <dir>   # 在任意含 app/ 的目录下
```

**依赖**（首次使用需安装）：

```bash
pip install -r ~/.workbuddy/skills/ride-screenshot-georeference/assets/ride_core/requirements.txt
```

常用参数：`--online`（允许调用在线地理编码，需已配 `AMAP_KEY` 等密钥）、
`--no-chart`（跳过轨迹图）、`--no-road-verify`（跳过路网验证图，省一次网络请求）。

## 产出文件

| 文件 | 用途 |
|---|---|
| `trajectory_gcj02.geojson` | **GCJ-02 基准**。腾讯/高德/美团底图直接用这份 |
| `trajectory_wgs84.geojson` | WGS-84 基准。GPS 设备、Strava、Garmin、GIS 工具用 |
| `overlay_result.png` | 原截图 + 识别轨迹叠加（橙线=轨迹，白点=采样点，绿=起点，红=终点，青圈=锚点） |
| `trajectory_chart.png` | 独立轨迹图（米制等比例，标路名与公里刻度） |
| `road_verify.png` | OSM 道路几何投影回截图 + 白色轨迹（验证绝对位置用） |

**坐标系是交付时必须说清的事**：中国境内两个基准相差约 500 米，把 WGS-84 直接
画在中文底图上必然偏离道路。用户说「轨迹不在路上」时，**先确认他加载的是哪个
文件**——这是最常见的原因，其次才是算法问题。

## 结果解读：怎么判断这次识别可不可信

摘要里的关键字段：

| 字段 | 含义 | 判读 |
|---|---|---|
| `confidence` | 综合置信度 | < 0.6 属「识别成功但建议核对」，要在交付时说明 |
| `diagnostics.anchor_backproj_px` | 锚点真值反投影回像素的偏移中位 | 越小越好；> 100 px 说明绝对位置存疑 |
| `diagnostics.model` | 配准模型 | `north_up` 最可靠；`affine` 说明锚点噪声大 |
| `road_fit.median_before_m` → `median_after_m` | 路网校正前后的贴路距离 | 明显改善说明锚点有系统性偏差并已被纠正 |
| `road_fit.shift_e_m` / `shift_n_m` | 路网校正的平移量 | 若超过 300 m，务必人工核对 |
| `warnings` | 全部告警 | **必须逐条读**，里面有「N/M 个锚点匹配到坐标」「路网精修未采纳」等关键信息 |

**交付前必做的一步**：打开 `overlay_result.png` 看轨迹是否贴着 App 自己画的那条
灰色轨迹线。数字漂亮不等于结果对——反投影自洽只能证明内部一致，不能证明绝对
位置正确。

## 硬性规则（违反就会出错）

1. **绝不重复换算基准**。`geojson_gcj02` 里的坐标已经是 GCJ-02，再套一次
   `wgs84_to_gcj02` 会凭空多出约 500 米偏移。画叠加图只能用配准矩阵的逆。
   这是本项目踩过两次的坑，两次都表现为「轨迹明显偏离原图」却一度怀疑算法。
2. **验证绝对位置要用第三方数据**，不能只靠内部自洽。最硬的判据是「截图自己
   渲染的路网」：美团底图道路比背景更蓝（`b - r ≥ 28`），据此提取掩膜，再把
   OSM 路网投影回截图统计命中率。
3. **单一指标变好 ≠ 位置更准**。那一带常有平行道路（相距 100–300 m），
   「到最近道路距离最小」会被骗。必须有正交证据（如 App 自己的路名标签 ↔
   OSM 同名道路中心线的距离，路名是印在路面上的）。
4. **不要用「横向延展」这类形状启发式**筛选连通域。对角线或南北向路线会被整条
   漏掉。判据应是拓扑：连通域必须同时靠近「起」「终」两个徽章。

## 排查指引

当用户说结果不对时，按这个顺序查（详见 `references/methodology.md`）：

1. 加载的是 GCJ-02 还是 WGS-84？→ 坐标系错位
2. 看 `overlay_result.png`，轨迹是否与 App 画的灰线重合？→ 像素级提取问题
3. 看 `road_verify.png`，OSM 路网是否压在 App 渲染的路网上？→ 基准或数据源问题
4. 看 `road_fit.shift_*`，平移量是否异常大？→ 锚点系统性偏差（词典问题）
5. 看 `warnings` 里锚点匹配率 → 词典覆盖不足（换城市会直接失败）

## 扩充城市 / 修正路名

本地词典 `D:\Dev\meituan-ride\data\lexicon.json` 是识别结果的唯一数据来源
（当前仅覆盖上海 38 个 POI）。两条扩充路径：

- 配 `AMAP_KEY` 环境变量：启用在线地理编码（高德与美团底图同源，POI 标注位置
  最一致，精度优于本地词典）
- 在网页上点选纠正：`http://127.0.0.1:8848` 的纠正入口会把坐标写回词典并提升权重

## 已知限制

- 只支持**美团系截图**（绿色「起」+ 红色「终」水滴徽章、灰白骑行轨迹线）。
  其他 App（如 Keep 的花瓣地图底图）需要单独适配。
- 截图**不含时间戳**，产出只能做轨迹/里程/空间分析，不能直接当 FIT/GPX 运动记录。
- 精度天花板约 10–30 米：1 像素 ≈ 4–5 米，且 POI 文字标注本身有 35–150 米固有偏移。
